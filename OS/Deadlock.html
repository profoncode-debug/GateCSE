Deadlock

Core concepts, illustrations, and explanations for GATE revision.

01

Introduction to Deadlock

Deadlock is a situation in which a set of processes is permanently blocked because each process is waiting for a resource held by another process in the same set.

The Dining Philosophers Problem

Four people, A, B, C, and D, sit around a circular table with four shared forks, one between each pair of neighbours. Each person needs both adjacent forks to eat. A fork can be held by only one person at a time.

Dining exampleOperating Systems equivalent
People A, B, C, DProcesses
Shared forksExclusive resources
EatingExecuting a task requiring both resources

How Does Deadlock Occur?

  1. Initially, all four forks are free. Each person picks up their left fork.
  2. Every person now holds one fork and waits for the other, which a neighbour holds.
  3. If everyone keeps their first fork until they can eat, nobody can proceed or release a fork. The group is deadlocked.

The allocation causes the problem. There are enough forks for one person to eat. If A receives both adjacent forks, A can finish and release them, allowing others to proceed. Deadlock is possible under the described acquisition rule; it is not inevitable.

02

Conditions to Deadlock

Deadlock requires the following four necessary conditions, called the Coffman conditions, to hold simultaneously.

1. Mutual Exclusion

At least one resource is non-shareable: only one process can use it at a time. Other processes requesting it must wait until it is released.

Dining example: A fork can be held by only one person at a time.

2. Hold and Wait

A process holds at least one resource while waiting to acquire additional resources held by other processes.

Dining example: Each person holds one fork while waiting for the second fork.

3. No Preemption

A resource already granted to a process cannot be forcibly taken away. It must be released voluntarily by the process holding it.

Dining example: A fork cannot be taken from its holder; the person must put it down.

This concerns preemption of resources, not CPU scheduling or preemption of processes. Switching a process off the CPU does not automatically release the resources it holds.

4. Circular Wait

A circular chain of processes exists in which each process waits for a resource held by the next process in the chain.

Dining example: A waits for B's fork, B for C's, C for D's, and D for A's.

A → B → C → D → A

All four are necessary. Breaking any one prevents deadlock. A system that permits all four conditions is not necessarily deadlocked at every moment; the current allocation and outstanding requests matter.

03

Resource Allocation Graph (RAG)

A Resource Allocation Graph is a directed graph representing resources allocated to processes and outstanding requests for additional resources. It shows who holds a resource and who is waiting for one, helping us analyse deadlock.

Nodes and Edges

A RAG contains two types of nodes and two types of directed edges:

SymbolNameMeaning
Circle labelled PiProcess nodeA process in the system.
Rectangle labelled RjResource-type nodeA resource type; each dot or small square inside represents one instance.
Pi → RjRequest edgePi has requested an instance of Rj and is waiting to acquire it.
Rj instance → PiAssignment edgeA particular instance of Rj is allocated to Pi.

Direction matters: P → R means “wants”; R → P means “holds”. A request points to a resource type; an assignment starts from a specific instance inside its rectangle.

Resource Type vs. Resource Instance

One resource type can have multiple interchangeable instances. If R1 represents four identical printers, draw one rectangle containing four markers, one per printer.

A resource type describes a category; an instance is one unit of that category. This distinction matters when interpreting cycles.

Example: Two Processes Waiting for Each Other

Consider two processes, P1 and P2, and two resource types, R1 and R2, each with one instance. P1 holds R1 and requests R2; P2 holds R2 and requests R1. Assume resources cannot be forcibly taken away and each process keeps its current resource while waiting.

  • R1 → P1: P1 holds R1.
  • P1 → R2: P1 is waiting for R2.
  • R2 → P2: P2 holds R2.
  • P2 → R1: P2 is waiting for R1.

Deadlock has occurred: P1 needs R2, which P2 holds; P2 needs R1, which P1 holds. Neither can proceed and release the resource the other needs.

Reading cycles: In the standard RAG model for reusable, non-preemptible resources, no cycle means no deadlock. When every resource type has a single instance, a cycle implies deadlock. With multiple instances, a cycle indicates a possibility of deadlock but does not by itself prove it.

Example: A Cycle Without Deadlock

Consider the supplied system snapshot. R1 has one instance, allocated to P1. R2 has two instances: one is allocated to P2 and the other is free. P1 requests one instance of R2, while P2 requests R1.

The graph contains the cycle P1 → R2 → P2 → R1 → P1. However, P1 does not have to wait for the particular R2 instance held by P2: it can receive the other, free instance.

  1. Allocate R2's free instance to P1, satisfying its outstanding request.
  2. Assuming no further requests, P1 can complete and release its instances of R1 and R2.
  3. Allocate the released R1 instance to P2. P2 can then complete and release its resources.

Possible completion sequence: P1 → P2   ⇒   No deadlock

A cycle alone is not sufficient with multiple instances. Check whether an outstanding request can be satisfied by a free instance, allowing a process to finish and release resources. This snapshot has a cycle but is not deadlocked.

Cycles and Deadlock: Single vs. Multiple Instances

For reusable, non-preemptible resources in the standard RAG model, the meaning of a cycle depends on the number of instances per resource type.

Resource modelRelationshipWhat can we conclude?
Every resource type has a single instanceCycle ⇔ DeadlockA cycle is both necessary and sufficient for deadlock.
Resource types may have multiple instancesDeadlock ⇒ Cycle, but Cycle ⇏ DeadlockA cycle is necessary, but not sufficient. Check instance availability and whether processes can finish and release resources.
Either modelNo cycle ⇒ No deadlockWithout a cycle, the system is not deadlocked.

Why Can a Cycle Exist Without Deadlock?

Suppose R1 has two instances. Even if one instance is allocated, a requesting process may obtain the other if it is free. That process can finish and release resources, allowing other processes to proceed and breaking the cycle.

Even when no instance is initially free, a process outside the cycle may finish and release one. This is what happens in the four-process example, where P2 or P4 can complete first.

Multiple instances do not rule out deadlock. They mean that a cycle alone cannot prove it. Another instance must actually be available, or become available through a process that can make progress; merely having additional instances does not guarantee that the cycle will disappear.

04

Deadlock Prevention Techniques

Deadlock prevention uses restrictions on resource requests or allocation so that deadlock cannot occur. Classical prevention breaks at least one of the four necessary conditions. The following example establishes a deadlock-free resource count under bounded process demands.

Example: How Many Resource Instances Are Sufficient?

Given:

  • There are 3 processes: P1, P2, and P3.
  • Each process may require at most 3 resource instances in total.
  • Instances are allocated one at a time.

Question: What is the minimum number of resource instances sufficient to guarantee that deadlock can never occur?

Model: All instances belong to one resource type and are interchangeable. A process may retain its allocated instances while requesting more, but completes and releases them once its total requirement is satisfied. The maximum of 3 includes instances already held.

Why Can Six Instances Allow Deadlock?

Consider the worst case: each process needs all 3 instances and has already received 2. All 6 instances are held, and each process is waiting for one more. None can complete and release its resources.

Worst-case allocation before any process can finish
Total instancesP1 holds / still needsP2 holds / still needsP3 holds / still needsFree instancesOutcome
62 / 12 / 12 / 10Deadlock is possible
72 / 12 / 12 / 11A process can receive its final instance

Why Do Seven Instances Guarantee Progress?

  1. Even if all three processes hold 2 instances each, the seventh instance remains free.
  2. Give it to P1. P1 now has its maximum requirement of 3, so it can complete and release all 3 instances.
  3. Give one of those released instances to P2. It can complete and release its resources.
  4. P3 can then obtain its final instance and complete.

More generally, if no process can finish yet, each can hold at most 2 instances. Together they can hold at most 6, so with 7 instances there must be a free instance to satisfy another one-at-a-time request. If some process already has its full requirement, it can finish instead.

3 × (3 − 1) + 1 = 6 + 1 = 7 resource instances

Answer: 7. Six instances do not guarantee deadlock freedom; they can produce the allocation above. Seven guarantee that the system cannot become deadlocked under the stated model. With six, deadlock is possible rather than inevitable.

General Formula: One Resource Type

For n processes, each requiring at most k instances of one resource type, with requests granted one instance at a time:

Minimum total instances guaranteeing no deadlock = n(k − 1) + 1

Each process can hold k − 1 instances and still wait for one more. Thus, n(k − 1) instances can all be held without anyone being able to finish. One extra instance guarantees that at least one process can make progress, finish, and release its resources.

This bound assumes interchangeable instances, bounded total requirements, and release on completion. It does not directly apply to multiple resource types or requests that must be granted in larger batches.

Question: GATE CSE 1992 · 02-xi

A computer system has 6 tape devices, with n processes competing for them. Each process may need 3 tape drives. The maximum value of n for which the system is guaranteed to be deadlock-free is:

  1. 2
  2. 3
  3. 4
  4. 1

Solution

Treat the tape drives as interchangeable instances of one resource type, acquired one at a time and released on completion. Each process may require all 3 drives, so use the worst-case demand rather than assuming it will finish with fewer.

For n processes with a maximum demand of 3 drives each, the minimum total guaranteeing no deadlock is n(3 − 1) + 1. With 6 drives available:

6 ≥ n(3 − 1) + 1   ⇒   2n ≤ 5   ⇒   n ≤ 2.5

Since n is an integer, its maximum value is 2.

  • With 2 processes: if both hold 2 drives and need one more, only 4 drives are held and 2 remain free. At least one process can obtain its third drive, finish, and release its drives.
  • With 3 processes: each can hold 2 drives and wait for a third. All 6 drives are then held, so no process can finish. Deadlock is possible.

nmax = ⌊(6 − 1) / (3 − 1)⌋ = 2

Correct answer: A. 2. The question asks for a guarantee under any permitted allocation. Three processes might finish under a favourable allocation, but they are not guaranteed to remain deadlock-free.

Question: GATE CSE 2018 · Question 24

Consider a system with 3 processes that share 4 instances of the same resource type. Each process can request a maximum of K instances. Resources can be requested and released only one at a time. The largest value of K that will always avoid deadlock is ________.

Solution

Interpret K as the maximum total number of instances a process may need simultaneously, including those it already holds. In the worst case, each of the three processes holds K − 1 instances and waits for one more. Together, they can hold 3(K − 1) instances without reaching their maximum requirement.

One additional instance lets a process obtain its final resource, finish, and release its instances. Therefore, the required total for a deadlock-free guarantee must not exceed the four available instances:

3(K − 1) + 1 ≤ 4

3K − 2 ≤ 4   ⇒   3K ≤ 6   ⇒   K ≤ 2

Since K is an integer, its largest permitted value is 2.

Check the Boundary

  • K = 2: if each process holds one instance and needs one more, three instances are held and the fourth is free. Give it to any process; that process can finish and release both instances. The others can then proceed.
  • K = 3: an allocation of (2, 1, 1) uses all four instances. If every process requests one more while retaining its allocation, nobody can proceed. Thus K = 3 does not guarantee deadlock freedom.

Kmax = ⌊(4 − 1) / 3⌋ + 1 = 2

Answer: 2. Use an inequality because the available instances must be at least the required bound. Setting 3(K − 1) + 1 = 4 also gives K = 2 here; it does not give K = 3.

  1. 3

05

Dealing with Deadlock

There are four broad strategies for handling deadlocks: ignore the problem, prevent it, avoid it, or detect it and recover.

1. Ignore the Problem — The Ostrich Algorithm

The Ostrich Algorithm makes no special attempt to prevent, avoid, or detect deadlock for the resources covered by this policy. It proceeds as though deadlocks will not occur, accepting the possibility rather than paying the cost of actively handling it.

The name is a metaphor for “putting one's head in the sand” and ignoring a problem.

How Is a Problem Handled?

  • If an application or system appears deadlocked or stops functioning, a user or administrator may intervene manually.
  • Intervention may involve terminating the affected application or restarting the system when necessary.
  • A system may also be temporarily frozen because of slow I/O or heavy load. An apparent freeze alone does not prove deadlock.

Why Use This Approach?

It can be reasonable when deadlocks are infrequent and the overhead or restrictions of prevention, avoidance, or detection would cost more than occasional manual intervention.

The slide cites general-purpose operating systems, including UNIX, as examples. Interpret this as ignoring some classes of deadlock, rather than assuming every subsystem ignores every kind of deadlock.

Ignoring is not prevention. The system can still enter deadlock. Manual recovery after a suspected hang is different from running an automatic deadlock-detection algorithm.

2. Deadlock Prevention

Deadlock prevention imposes rules that make at least one of the four necessary conditions impossible. If even one condition never holds, deadlock cannot occur.

Let M = mutual exclusion, H = hold and wait, N = no preemption, and C = circular wait:

Deadlock ⇒ M ∧ H ∧ N ∧ C

¬M ∨ ¬H ∨ ¬N ∨ ¬C ⇒ No deadlock

Mutual Exclusion: Cannot Generally Be Eliminated

A non-shareable resource can be used by only one process at a time. For example, two processes cannot independently print different documents on the same physical printer simultaneously without interfering with the output.

Allow sharing where it is safe, such as concurrent access to a read-only file. However, inherently non-shareable resources still require mutual exclusion, so this is not a universal prevention method.

Hold and Wait: Can Be Eliminated

Normally, P1 might hold R1 while requesting R2. If R2 is unavailable, P1 waits while retaining R1. Prevent this using either of these rules:

  • Request everything together: P1 requests R1 and R2 as a single all-or-nothing allocation. Grant both only when both are available; otherwise, P1 waits holding neither.
  • Release before requesting: require P1 to release all currently held resources before requesting a new set. It can request the old resources again along with the new ones.

Disadvantages: reserving resources before they are needed can reduce utilisation. A process needing several resources together may repeatedly lose out to others and suffer starvation.

No Preemption: Can Sometimes Be Eliminated

If P1 holds R1 and requests an unavailable R2, a preemption policy can withdraw suitable resources already allocated to P1. P1 retries later when it can obtain the resources it needs. This prevents it from indefinitely retaining resources while blocked.

This works only where the resource's state can be saved, restored, or safely rolled back. Taking a physical printer away halfway through a document can leave incomplete output, so arbitrary preemption is not suitable for every resource.

Resource preemption is different from CPU preemption. Descheduling P1 does not release R1. Voluntarily releasing all held resources before a new request is the hold-and-wait restriction above; enforced withdrawal of an allocated resource breaks no preemption.

Circular Wait: Can Be Eliminated

Each process can request resources only in an increasing order of enumeration. Assign all resource types a fixed numerical order, shared by every process:

R1 < R2 < R3 < R4 < R5

If a process holds Ri, it may request Rj only when j > i. If it holds several types, the new type must have a higher rank than every type it currently holds.

  • A process holding only R2 may request R3, R4, or R5.
  • It cannot request R1 while retaining R2, because 1 < 2.
  • A process with no resources may initially request any resource type; it does not have to start with R1.

This technique is called resource ordering. A request forbidden by the ordering rule is disallowed even if the requested resource happens to be free.

Example: Printer, Scanner, and Disk

Let R1 = Printer, R2 = Scanner, and R3 = Disk, with the fixed order R1 < R2 < R3. For this conceptual example, assume one exclusive instance of each resource.

ProcessHoldingWants to requestAllowed under resource ordering?
P1R1: PrinterR2: ScannerYes, because 2 > 1.
P2R2: ScannerR3: DiskYes, because 3 > 2.
P3R3: DiskR1: PrinterNo, because 1 < 3.

Without ordering, all three requests could remain outstanding, giving the circular wait P1 → P2 → P3 → P1. With ordering, P3 cannot request R1 while holding R3, so the final dependency cannot form.

P3 must release R3 before requesting R1 in a new acquisition sequence. If it then needs both resources, it acquires R1 before R3. More generally, it must release any retained resource whose rank is not lower than the new request.

Why a cycle is impossible: imagine 20 resource types. Dependencies may progress from R3 to R8 to R15 to R20, but a process retaining R20 cannot request R3, R8, or R15:

R3 < R8 < R15 < R20   —   no permitted return to R3

A circular wait would require resource ranks to increase strictly around a loop and return to the starting rank, implying rank(R) < rank(R). This is impossible. Preventing circular wait therefore prevents deadlock.

For resource types with multiple instances, request all needed instances of a type together; later requests while retaining them must be for higher-ranked types.

3. Deadlock Avoidance

Examine each resource request and grant it only if the resulting state remains safe: there is an order in which all processes can obtain their remaining requirements and finish.

Avoidance needs advance information about possible resource demands. Banker's algorithm is a classic example. An unsafe state is not necessarily already deadlocked; it lacks a guarantee that every process can finish.

Safe State vs. Unsafe State

A safe state is a state in which at least one safe sequence of processes exists. In that order, every process can obtain its remaining required resources, complete, and release its resources for the processes that follow.

A safe state therefore guarantees that deadlock can be avoided through proper resource allocation. It does not require enough resources for every process to receive its maximum demand simultaneously.

An unsafe state is a state in which no safe sequence exists. The OS cannot guarantee that every process will complete if processes request their maximum remaining resources.

Unsafe does not necessarily mean already deadlocked. Actual processes may request less than their declared maximum or release resources earlier, allowing progress. Deadlock is possible depending on subsequent requests and allocations.

StateSafe sequence exists?Meaning
SafeYesProper allocation can guarantee completion, even for declared maximum demands.
UnsafeNoCompletion cannot be guaranteed; deadlock may or may not already exist.
DeadlockedNoA set of processes is already blocked waiting for resources that cannot be released without intervention.

Safe State ⇒ No Deadlock   |   Deadlock ⇒ Unsafe State

Unsafe State ⇏ Deadlock

Every deadlocked state is unsafe, but an unsafe state is not necessarily deadlocked. Banker's algorithm rejects allocations that would enter an unsafe state, before deadlock can develop.

Banker's Algorithm

Banker's algorithm grants a resource request only if a trial allocation leaves the system in a safe state. Like a banker keeping enough funds to meet commitments, the OS checks that every process can still finish in some order, assuming each may require its declared maximum.

QuantityMeaning

For multiple resource types, Available is a vector and Allocation, Max, and Need are matrices. Comparisons must hold for every resource type. This example uses one type, so each value is a single count.

The system has 12 interchangeable tape drives. Interpret the slide's “current usage” as Allocation and “could ask for” as remaining Need, not maximum total demand.

Checking a New Resource Request

  1. Check Request ≤ Need; a request exceeding the declared remaining claim is invalid.
  2. Check Request ≤ Available; otherwise, the process must wait.
  3. Try the allocation: subtract Request from Available, add it to the process's Allocation, and subtract it from its Need.
  4. Run the safety test. Commit the allocation only if the result is safe; otherwise restore the original values and make the process wait.

Example: Should P2 Receive One More Tape Drive?

Return to the 12-drive snapshot. Its initial state is safe, with the sequence P1 → P0 → P2. Now P2 requests one additional drive. Its request is within its remaining claim of 7 and the 3 currently available drives, but we must still test the resulting state.

Before and after a tentative grant of one drive to P2

Available before = 12 − (5 + 2 + 2) = 3   →   Available after trial = 2

P2's maximum claim stays 9: Allocation increases by 1 while Need decreases by 1. Test the trial state with Work = 2:

  1. P1 can finish: its Need is 2. After simulated completion, Work becomes 2 + 2 = 4.
  2. P0 cannot be marked finished: its Need is 5, but Work is only 4.
  3. P2 cannot be marked finished: its Need is 6, also greater than 4. No further process can be selected, so no safe sequence exists.

Trial grant to P2 ⇒ Unsafe state ⇒ Defer the request

What happens next? Roll back the trial grant, restoring Available = 3, P2 Allocation = 2, and P2 Need = 7. P2 waits while the system permits requests that preserve safety.

For example, P1 can receive its remaining 2 drives, finish, and release all 4 it then holds. Available becomes 3 − 2 + 4 = 5. If P2's one-drive request is retried now, the trial state has Available = 4 and Need values (5, 6) for P0 and P2; it is still unsafe. Instead, P0 can receive its remaining 5 drives and finish, leaving 10 drives free while P2 retains its original 2. P2's request can then be safely granted: Available becomes 9, enough to cover its remaining Need of 6.

Retry the safety test when resources are released. Another process finishing does not automatically make a waiting request safe. Here, waiting for P1 and then P0 to finish makes P2's allocation safe. The unsafe trial state is not itself proof of an existing deadlock.

Available does not automatically mean safe to allocate. Banker's algorithm preserves a possible completion order. An unsafe state need not already be deadlocked; it lacks the guarantee of completion if processes demand their full remaining claims.

Question: A System Has Only One Safe Sequence

Let ⟨P1, P2, …, Pn⟩ be the only safe sequence of a system. Which of the following is/are always true?

  1. If P2 is the first process to request some resources, P2 always has to wait.
  2. P1's requests will always be satisfied without even checking whether the resulting state is safe.
  3. Process requests will always be satisfied in the same order as the safe sequence; no out-of-order process request can be satisfied.
  4. We can never satisfy any request from Pn without first satisfying a request from P1.

Terminology: The slide says “only safe state”, but the ordered list is a safe sequence. Assume requests are within declared remaining claims and processes do not increase their maximum claims. Under these standard assumptions, only B is always true.

Why B Is True

Because P1 is first in a safe sequence, Need(P1) ≤ Available for every resource type. Any valid request r from P1 satisfies r ≤ Need(P1), so it is available and can be granted.

After the grant, P1's remaining Need and Available both decrease by r. P1 can still finish first. Its simulated completion leaves exactly the same free resources as completing it before the grant:

Work after P1 finishes = (Available − r) + (Allocation(P1) + r)

= Available + Allocation(P1)

The rest of the original safe sequence remains feasible. Therefore, a separate safety test is unnecessary for this particular valid grant to P1. This property does not depend on the safe sequence being unique.

One Counterexample Disproves A, C, and D

Take two processes and 4 instances of one resource type:

ProcessAllocationMaxNeed
P1121
P2143

Available = 4 − (1 + 1) = 2. P1 can finish because its Need is 1. P2 cannot finish first because its Need is 3. After P1 finishes, Work becomes 3, allowing P2 to finish. Thus, ⟨P1, P2⟩ is the only safe sequence.

Now suppose P2 makes the first request, for just one instance. Granting it produces:

ProcessAllocation after grantNeed after grant
P111
P222

Available is now 1. P1 can still finish, raising Work to 1 + 1 = 2; then P2 can finish, raising Work to 2 + 2 = 4. The grant is safe even though P2 requested before P1.

  • A is false: P2's first request can be granted immediately; it does not always have to wait.
  • C is false: P2 can receive a partial allocation before P1, despite appearing later in the safe sequence.
  • D is false: here n = 2, so Pn is P2. Its request was granted before any request from P1. A universal claim must also hold for this two-process case.

Not every P2 request is safe: from the original snapshot, granting P2 two instances would leave Available = 0 and both processes with Need = 1. Neither could finish, so that request must wait.

Answer: B only. A safe sequence gives a feasible order of completion, not a compulsory order for every intermediate allocation. Later processes may receive resources earlier if the resulting state stays safe.

Question: Two Independent Resource Requests

An operating system uses Banker's Algorithm for deadlock avoidance while managing three resource types X, Y, and Z for processes P0, P1, and P2. The current Allocation and Max matrices are:

ProcessAllocation (X, Y, Z)Max (X, Y, Z)

The system is currently safe. Consider the following independent requests:

  • REQ1: P0 requests (0, 0, 2).
  • REQ2: P1 requests (2, 0, 0).

Which one of the following is true?

  1. Only REQ1 can be permitted.
  2. Only REQ2 can be permitted.
  3. Both REQ1 and REQ2 can be permitted.
  4. Neither REQ1 nor REQ2 can be permitted.

Solution: Calculate the Initial Need

Use Need = Max − Allocation. Every vector below follows the order (X, Y, Z).

ProcessInitial Need
P0(8, 4, 2)
P1(3, 0, 0)
P2(1, 2, 2)

The original state has the safe sequence P1 → P2 → P0, with Work progressing from (3, 2, 2) to (6, 4, 2), then (8, 5, 3), and finally (8, 5, 4).

Independent requests: evaluate each request from the original Allocation, Need, and Available values. Do not carry REQ1's trial changes into the test for REQ2.

REQ1: P0 Requests (0, 0, 2)

The request is within both P0's Need and Available, so the preliminary checks pass. After a trial grant:

  • Available: (3, 2, 0).
  • P0 Allocation: (0, 0, 3).
  • P0 Need: (8, 4, 0).

  • P0 cannot finish: it needs 8 units of X, but only 6 are available.
  • P2 cannot finish: it needs 2 units of Z, but none are available.

No safe sequence exists after the trial grant. REQ1 must be deferred; restore the original state.

REQ2: P1 Requests (2, 0, 0)

Starting again from the original snapshot, this request also passes the Need and Available checks. After a trial grant:

  • Available: (1, 2, 2).
  • P1 Allocation: (5, 2, 0).

4. Deadlock Detection and Recovery

Allow resource allocations that may lead to deadlock, then run a detection procedure to determine whether deadlock has occurred.

After detection, recover by terminating selected processes or reclaiming resources where preemption and rollback are possible. Detection identifies the problem; recovery breaks it.
