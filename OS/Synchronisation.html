Operating Systems

Process Synchronisation

Detailed concepts, execution flows, distinctions, and exam-ready notes for GATE revision.

01

Atomic Operations

An atomic operation executes as one indivisible unit with respect to other threads. Once it begins, no other thread can observe a partially completed result or interleave a conflicting operation in the middle of it.

A single statement in a high-level language is not necessarily atomic. Suppose the shared variable is initially x = 50, and two threads T1 and T2 both execute:

x = x + 1;

At the C-language level, this appears to be one statement. Internally, however, the processor may need several assembly-like instructions to complete it:

LOAD  R1, x      // copy x from memory into register R1
ADD   R1, 1      // increment the value held in R1
STORE x, R1      // copy the result from R1 back to x

Thus, the statement is conceptually a read–modify–write sequence rather than one indivisible action.

LOAD (read)  →  ADD (modify)  →  STORE (write)

Execution Without Interruption

If only T1 executes the sequence, it reads 50, changes its register value to 51, and stores 51 in shared memory. The result is correct:

Initial value:   x = 50

T1: LOAD  R1, x     → R1 = 50
T1: ADD   R1, 1     → R1 = 51
T1: STORE x, R1     → x  = 51

Execution With a Context Switch

The problem appears if T1 is interrupted after performing LOAD and ADD, but before performing STORE. At that moment, T1 has calculated 51 in its register, yet shared memory still contains x = 50.

When T2 starts, it also reads 50 because T1 has not yet updated memory. T2 calculates 51 and stores it. Later, T1 resumes with its previously calculated value restored as part of its thread context and also stores 51.

Each thread incremented x once, so the expected result is:

50 + 1 + 1 = 52

Instead, the final result is x = 51. Both threads computed their answer from the same old value, so one increment had no visible effect. This is the lost update problem, a classic example of a race condition.

Register note: Although both instruction sequences use the name R1, each thread has its own saved register state. During a context switch, the operating system saves the outgoing thread's register values and later restores them when that thread resumes.

The solution is to ensure that the complete read–modify–write sequence for the shared variable behaves atomically with respect to other threads. In other words, no competing thread should be allowed to enter between the LOAD, ADD, and STORE steps.

Key point: One line of source code does not imply one machine instruction. Whenever a shared value is read, modified, and written using multiple instructions, synchronisation may be required to make the overall operation safe.

02

Critical Section Problem

A critical section is the part of a process or thread that accesses shared data or a shared resource. To prevent race conditions, a correct synchronisation mechanism must ensure that at most one process executes its critical section at a time.

Consider two threads, T1 and T2, that both execute the following statement on the shared variable x:

x = x + 1;

As seen earlier, the statement may be implemented as multiple machine instructions. If the two threads interleave those instructions, an update can be lost. The most direct solution is to place the shared-data operation inside a protected region. This protected region is the critical section.

Thread T1

T1 {
    // critical section
    x = x + 1;
}

Thread T2

T2 {
    // critical section
    x = x + 1;
}

The two critical sections contain operations on the same shared variable, so they must not execute simultaneously. If one thread is inside its critical section, the other must wait until the first thread leaves.

Mutual exclusion: At most one process or thread can be inside the critical section at any given time.

Execution With Mutual Exclusion

Suppose x initially contains 50 and T1 enters the critical section first. T2 cannot enter while T1 is inside, so each increment completes before the next one begins.

The final value is now x = 52, which is correct. Mutual exclusion converts the two unsafe, potentially overlapping read–modify–write sequences into two safely ordered operations.

Why “At Most One”?

The requirement says at most one, not exactly one. A critical section may contain:

  • zero processes when no process currently needs the shared resource; or
  • one process when a process is safely using the shared resource.

It must never contain two or more processes at the same time.

Number of processes inside the critical section ≤ 1

Not allowed

2 or more processes inside the critical section simultaneously.

Exam summary: Code that accesses shared data forms a critical section. The first major requirement of the Critical Section Problem is mutual exclusion: at most one process or thread may execute the critical section at a time.

03

Solution of Critical Section Problem

A correct solution to the Critical Section Problem must satisfy three conditions: Mutual Exclusion, Progress, and Bounded Waiting. Together, they provide safety, forward movement, and fairness.

01 · Safety

Mutual Exclusion

No two processes may be inside their critical sections at the same time.

02 · Movement

Progress

If the critical section is free and processes want to enter, one must eventually be selected.

03 · Fairness

Bounded Waiting

A requesting process cannot be overtaken indefinitely by other processes.

1. Mutual Exclusion

Mutual Exclusion means that at any instant, at most one process is allowed to execute inside the critical section. Because the critical section accesses or modifies shared data or a shared resource, allowing two processes to enter together may cause interference and produce a race condition.

A correct synchronisation mechanism must therefore maintain the following condition:

Number of processes in the critical section ≤ 1

The phrase at most one is important. Zero processes inside the critical section is valid, and one process inside is also valid. Two or more processes inside simultaneously violates mutual exclusion.

Memory phrase: Mutual Exclusion is the “at most one” condition.

2. Progress

Progress means that if the critical section is empty and one or more processes want to enter, the system must eventually allow at least one interested process to enter. The decision about who enters next cannot be postponed indefinitely.

For example, if P1 and P2 both want to enter while the critical section is free, the synchronisation mechanism must eventually select one of them. Progress does not allow both processes to enter; Mutual Exclusion still restricts entry to one process at a time. Progress simply prevents the system from unnecessarily blocking everyone while the resource is available.

Only processes that want to enter the critical section should participate in the decision. A process executing in its remainder section must not prevent interested processes from making progress.

Memory phrase: Progress is the “at least one” condition when the critical section is free and there are interested processes.

Progress in Layman's Terms

The idea is to keep useful work moving. Either a process is already inside the critical section doing its work, or, if the critical section is empty and at least one process wants to enter, an interested process must eventually be allowed in to do its work. The system should not leave the critical section unused while everyone who needs it waits indefinitely.

This means the processes are making progress collectively: someone gets to do useful work. It does not promise that every individual waiting process gets its turn; that additional fairness requirement is addressed by Bounded Waiting.

3. Bounded Waiting

Bounded Waiting means that after a process requests entry into its critical section, there must be a finite limit on the number of times other processes may enter before that requesting process gets its turn.

A process may wait while another process is already inside, and some other processes may be allowed to enter before it. However, it must not be overtaken forever. Indefinite waiting of a ready process is called starvation.

Suppose P1 is waiting while P2 is using the critical section. After P2 exits, the mechanism should not repeatedly allow P2 or other processes to re-enter while P1 waits forever. The rule “do not allow immediate re-entry when others are waiting” captures the fairness intended by Bounded Waiting.

Key result: Bounded Waiting prevents starvation by guaranteeing that every requesting process gets a turn within a finite bound.

Bounded Waiting in Layman's Terms

Once a process p asks to enter, another process p′ must not keep bypassing it indefinitely. Think of waiting in a queue: a few others may go ahead, but there must be a fixed, finite limit on how many entries can occur before your turn.

Here, bypassing means another process enters the critical section while p's request is still pending. Bounded Waiting limits those entries; it does not necessarily specify a waiting time in seconds or require a strictly first-come, first-served order.

Remember the difference: Progress asks, “Will someone get to enter?” Bounded Waiting asks, “How many times can others enter ahead of this particular waiting process?”

Comparison of the Three Conditions

Condition Guarantee Prevents Quick Recall
Mutual Exclusion No two processes execute the critical section together. Race conditions caused by overlapping critical sections At most one
Progress If the critical section is free and processes are interested, one is eventually selected. Unnecessary indefinite postponement of the entry decision At least one proceeds
Bounded Waiting Every requesting process receives a turn after a finite number of entries by others. Starvation Finite waiting

Exam summary: Mutual Exclusion says no two processes may be inside together; Progress says that when the critical section is free, an interested process must eventually be selected; Bounded Waiting says a particular waiting process cannot be postponed forever. A proper solution must satisfy all three.

Strict Alternation

Strict Alternation is a software attempt to solve the Critical Section Problem for two processes, P0 and P1. It uses a shared integer variable named turn to decide which process may enter its critical section.

int turn = 1;

turn = 0 → P0 may enter   |   turn = 1 → P1 may enter

Process P0

while (true) {
    while (turn != 0);

    // critical section

    turn = 1;
    // remainder section
}

P0 waits until turn == 0. After leaving its critical section, it gives the turn to P1.

Process P1

while (true) {
    while (turn != 1);

    // critical section

    turn = 0;
    // remainder section
}

P1 waits until turn == 1. After leaving its critical section, it gives the turn to P0.

The semicolon after each inner while is intentional: the loop body is empty. A process repeatedly checks turn until it receives permission to enter. This continuous checking is called busy waiting.

How the Processes Alternate

Because the initial value is turn = 1, P1 can enter first. P0 remains in while (turn != 0);. When P1 finishes, it sets turn = 0, enabling P0. P0 later sets it back to 1.

turn = 1
P1 enters
→
P1 exits
turn = 0
→
P0 enters
→
P0 exits
turn = 1

P1 → P0 → P1 → P0 → …

The processes are forced to enter in this strict order, even if one of them does not currently need the critical section.

Checking the Three Requirements

Mutual Exclusion is satisfied. The shared variable can hold only one value at a time. When turn = 0, only P0 can cross its waiting loop; when turn = 1, only P1 can cross. Therefore, both processes cannot execute their critical sections simultaneously.

Bounded Waiting is satisfied. A process cannot repeatedly enter while the other is waiting. After leaving, it assigns the turn to the other process, so the two processes alternate.

Progress is not satisfied. Strict Alternation bases entry only on whose turn it is, not on whether that process actually wants to enter. Consequently, an uninterested process can prevent an interested process from entering an empty critical section.

Requirement Satisfied? Reason
Mutual Exclusion Yes Only the process identified by turn can enter.
Progress No An uninterested process may hold the turn and block the interested process.
Bounded Waiting Yes Neither process can take consecutive turns while the other is waiting.

Why Progress Fails

Suppose P1 finishes its critical section and sets turn = 0. It is now P0's turn, but P0 is doing other work and has no interest in entering the critical section. If P1 wants to enter again, it must wait in while (turn != 1);.

turn = 0

P0: not interested in the critical section
P1: wants to enter the critical section

Result: P1 keeps waiting because turn != 1

The critical section is empty, yet P1 cannot enter. Only P0 can change turn back to 1, and it does so only after entering and leaving its own critical section. Since P0 does not want to enter, P1 may remain blocked unnecessarily. This directly violates Progress.

Easy recall: Strict Alternation is safe and fair but unnecessarily restrictive. It forces processes to take turns even when one process does not want its turn.

2 Variables or Array Solution

Attempt 3 uses two shared Boolean flags, stored in an array named want[]. Each process raises its own flag to announce that it wants to enter the critical section, then checks the other process's flag before entering.

bool want[2] = {false, false};

want[0] = true → P0 wants to enter   |   want[1] = true → P1 wants to enter

Initially, both flags are false, meaning neither process is interested in entering the critical section.

Process P0

while (true) {
    want[0] = true;
    while (want[1]);

    // critical section

    want[0] = false;
    // remainder section
}

P0 announces its interest, then waits while P1's flag is true. After leaving the critical section, it lowers its own flag.

Process P1

while (true) {
    want[1] = true;
    while (want[0]);

    // critical section

    want[1] = false;
    // remainder section
}

P1 behaves symmetrically: it raises its flag, waits while P0 is interested, and lowers its flag after leaving.

Language note: The flags are conceptually Boolean. In C with <stdbool.h>, they can be declared as bool want[2] = {false, false};; pseudocode may instead write True and False.

Why Mutual Exclusion Is Satisfied

Suppose P0 is already inside the critical section. Its flag remains want[0] = true. If P1 tries to enter, it reaches while (want[0]); and must wait. The same reasoning applies in the opposite direction, so the two processes cannot be inside their critical sections simultaneously.

Simultaneous Requests Cause Deadlock

The serious failure occurs when both processes try to enter at nearly the same time. Each process may raise its own flag before either process checks the other's flag:

P0 sets
want[0] = true
→
P1 sets
want[1] = true
→
P0 sees
want[1] = true
↔
P1 sees
want[0] = true
want[0] = true
want[1] = true

P0 waits for P1
P1 waits for P0

Neither process enters the critical section.

P0 waits because P1's flag is true, while P1 waits because P0's flag is true. Neither process can reach the statement that lowers its flag because that statement appears after the critical section.

Both processes therefore remain blocked forever. This is a deadlock, and because the critical section is free but no interested process can enter, it is also a direct violation of Progress.

Checking the Three Requirements

Requirement Satisfied? Reason
Mutual Exclusion Yes A process waits whenever the other process's interest flag is raised.
Progress No If both flags become true, both processes wait even though the critical section is empty.
Bounded Waiting Not a useful guarantee The algorithm can deadlock, so requesting processes may never enter at all.

Core flaw: Each process raises its own flag before checking the other flag. If both flags are raised simultaneously, both processes politely wait for the other forever.

This failure motivates combining the interest flags with a tie-breaker such as turn. That combination leads to Peterson's solution.

Question: GATE CSE 2010 — Question 23

Consider the methods used by processes P1 and P2 for accessing their critical sections whenever needed, as given below. The initial values of shared Boolean variables S1 and S2 are randomly assigned.

Method used by P1

while (S1 == S2);
// Critical Section
S1 = S2;

Method used by P2

while (S1 != S2);
// Critical Section
S2 = !S1;

Which one of the following statements describes the properties achieved?

  1. Mutual exclusion but not progress
  2. Progress but not mutual exclusion
  3. Neither mutual exclusion nor progress
  4. Both mutual exclusion and progress

Correct answer: A — Mutual exclusion but not progress.

Step 1: Convert Waiting Conditions into Entry Conditions

A process crosses its empty while loop only when the loop condition becomes false. Therefore, P1 enters when S1 != S2, whereas P2 enters when S1 == S2.

S1S2P1P2
00WaitsMay enter
01May enterWaits
10May enterWaits
11WaitsMay enter

Step 2: Check Mutual Exclusion

Equality and inequality cannot hold simultaneously. While P1 is inside its critical section, the variables remain unequal and P2 waits. Only after P1 leaves does S1 = S2 make them equal, allowing P2 to enter.

Similarly, while P2 is inside, the variables remain equal and P1 waits. After P2 leaves, S2 = !S1 makes them unequal and allows P1 to enter. Thus, the processes cannot execute their critical sections together: Mutual Exclusion is satisfied.

Step 3: Check Progress with a Counterexample

Suppose S1 = 0 and S2 = 0. The critical section is empty, P1 wants to enter, and P2 is doing other work in its remainder section.

S1 = 0, S2 = 0

P1: while (S1 == S2);   // true: keeps waiting
P2: not interested in entering the critical section

Critical section: empty
P1: cannot enter

P1 cannot proceed until the variables become unequal. That requires P2 to enter, finish its critical section, and execute S2 = !S1. If P2 does not want to enter, P1 may wait forever despite the critical section being free. Therefore, Progress is violated.

Connection to Strict Alternation

Here, equality acts like P2's turn and inequality acts like P1's turn. Each exit statement hands permission to the other process. When both repeatedly request entry, the order strictly alternates; however, an uninterested process can prevent the other from entering.

Exam takeaway: Random initial values decide who gets the first turn. They do not fix the Progress problem. Always test the case where the critical section is empty and only the process without permission wants to enter.

Question: GATE CSE 2007 — Question 58

Two processes, P1 and P2, need to access a critical section of code. Consider the following synchronisation construct used by the processes:

Process P1

/* P1 */
while (true) {
    wants1 = true;
    while (wants2 == true);
    /* Critical Section */
    wants1 = false;
}
/* Remainder section */

Process P2

/* P2 */
while (true) {
    wants2 = true;
    while (wants1 == true);
    /* Critical Section */
    wants2 = false;
}
/* Remainder section */

Here, wants1 and wants2 are shared variables, which are initialized to false. Which one of the following statements is TRUE about the construct?

  1. It does not ensure mutual exclusion.
  2. It does not ensure bounded waiting.
  3. It requires that processes enter the critical section in strict alternation.
  4. It does not prevent deadlocks, but ensures mutual exclusion.

Correct answer: D — It does not prevent deadlocks, but ensures mutual exclusion.

Step 1: Understand the Entry Protocol

This is the same two-flag attempt discussed above. Each process first raises its own interest flag and then waits while the other process's flag is true. It lowers its flag only after finishing the critical section. As in the standard theoretical analysis, assume atomic flag reads and writes with instructions observed in program order.

Step 2: Why Mutual Exclusion Holds

If P1 is inside the critical section, wants1 remains true. P2 therefore cannot cross while (wants1 == true);. Similarly, P2's raised flag blocks P1 while P2 is inside.

More generally, both processes cannot pass their checks: the first process to raise its flag prevents the other from passing its check until that flag is lowered. If both raise their flags before checking, both wait. Thus, no execution permits simultaneous entry, and Mutual Exclusion is satisfied.

Step 3: A Deadlocking Interleaving

Initially, both flags are false. A context switch between a flag assignment and the following check can produce this execution:

StepActionwants1wants2
0Initial statefalsefalse
1P1 executes wants1 = true;truefalse
2P2 executes wants2 = true;truetrue
3P1 checks wants2 and waits.truetrue
4P2 checks wants1 and waits.truetrue

P1 needs P2 to clear wants2, and P2 needs P1 to clear wants1. Neither can reach its flag-clearing statement because both are stuck before the critical section. Even though they keep executing their busy-wait loops, neither makes useful progress. This is a deadlock.

The critical section is empty and both processes want to enter, yet neither can enter. Consequently, Progress is violated.

Step 4: Why the Other Options Do Not Describe the Construct

Option A is false: the flags do ensure mutual exclusion, as shown above.

Option B needs the formal definition: bounded waiting limits the number of entries by other processes after a request. Once a process raises its flag, the other process can complete at most one entry already permitted by an earlier check; it cannot repeatedly overtake the requester. The failure here is that both may stop entering altogether. A bound on overtaking alone does not guarantee progress, so D identifies the actual defect.

Option C is false: no variable forces alternating turns. If P2 has not raised its flag, P1 may enter, leave, and enter again. The algorithm checks interest rather than enforcing strict alternation.

Exam takeaway: Raising your own flag before checking the other flag preserves mutual exclusion but allows both flags to become true together. Both processes then wait forever: deadlock is possible, so choose D.

Question: GATE CSE 2015 — Set 3

Two processes X and Y need to access a critical section. Consider the following synchronisation construct used by both processes:

Process X

/* other code for process X */
while (true)
{
    varP = true;
    while (varQ == true)
    {
        /* Critical Section */
        varP = false;
    }
}
/* other code for process X */

Process Y

/* other code for process Y */
while (true)
{
    varQ = true;
    while (varP == true)
    {
        /* Critical Section */
        varQ = false;
    }
}
/* other code for process Y */

Here, varP and varQ are shared variables and both are initialized to false. Which one of the following statements is true?

  1. The proposed solution prevents deadlock but fails to guarantee mutual exclusion.
  2. The proposed solution guarantees mutual exclusion but fails to prevent deadlock.
  3. The proposed solution guarantees mutual exclusion and prevents deadlock.
  4. The proposed solution fails to prevent deadlock and fails to guarantee mutual exclusion.

Correct answer: A — The proposed solution prevents deadlock but fails to guarantee mutual exclusion.

Step 1: Read the Loop Body Carefully

Unlike the preceding two-flag algorithm, these inner while loops have bodies containing the critical sections. There is no semicolon immediately after the condition. When X sees varQ == true, it enters the loop body and executes the critical section. Y similarly enters when varP == true.

Exam trap: while (flag); repeatedly checks the flag without entering a critical section. Here, while (flag) { /* Critical Section */ } executes the critical section whenever the condition is true.

Step 2: Show a Mutual-Exclusion Violation

Consider this valid interleaving, starting with both flags false:

StepActionvarPvarQ
0Initial statefalsefalse
1X executes varP = true;.truefalse
2Y executes varQ = true;.truetrue
3X sees varQ == true and enters its critical section.truetrue
4Before X finishes, Y sees varP == true and enters its critical section.truetrue

At step 4, both processes are inside their critical sections. X has not yet reached varP = false;, so Y's condition is still true. This single counterexample proves that Mutual Exclusion is not guaranteed.

Step 3: Why There Is No Deadlock

Neither process waits in an empty loop for the other to lower its flag. If an inner condition is true, that process executes its critical section. If the condition is false, it skips the inner loop and continues its outer loop, setting its own flag to true again.

In particular, when both flags are true, both processes can enter rather than becoming stuck waiting for each other. Assuming processes continue to receive CPU time and their critical sections finish, there is no circular wait of the kind seen in the previous question. Thus, the construct prevents deadlock, although its shared-data access is unsafe.

Step 4: Eliminate the Other Options

B and C are false because both claim that mutual exclusion is guaranteed. D is false because the construct does not have the claimed deadlock failure. Only A matches both properties.

Exam takeaway: Both flags becoming true causes deadlock in the empty-wait-loop algorithm, but allows simultaneous critical-section entry in this algorithm. Always inspect the semicolon and braces before deciding what a while loop does.

Question: GATE CSE 2016 — Set 2, Question 48

Consider the following two-process synchronisation solution:

Process 0

Entry: loop while (turn == 1);
       (critical section)
Exit:  turn = 1;

Process 1

Entry: loop while (turn == 0);
       (critical section)
Exit:  turn = 0;

The shared variable turn is initialized to zero. Which one of the following is TRUE?

  1. This is a correct two-process synchronisation solution.
  2. This solution violates mutual exclusion requirement.
  3. This solution violates progress requirement.
  4. This solution violates bounded wait requirement.

Correct answer: C — This solution violates the Progress requirement.

Step 1: Recognise Strict Alternation

Process 0 waits while turn == 1, so it may enter when turn == 0. Process 1 waits while turn == 0, so it may enter when turn == 1. Each process hands the turn to the other on exit.

turn = 0 → P0 → turn = 1 → P1 → turn = 0 → …

When both processes repeatedly request entry, they enter in strict alternation, with P0 permitted first by the initial value.

Step 2: Mutual Exclusion Is Satisfied

The shared variable cannot be both 0 and 1 at the same time. While P0 is inside, turn remains 0 and P1 waits. P0 sets it to 1 only after leaving. The symmetric argument applies to P1. Thus, both processes cannot execute their critical sections simultaneously, ruling out option B.

Step 3: Progress Fails Even with an Empty Critical Section

Consider the initial state turn = 0. Suppose P0 does not want to enter, but P1 does:

turn = 0

P0: doing other work; does not request entry
P1: loop while (turn == 0);   // waits

Critical section: empty
Interested process: P1
Result: P1 cannot enter

Only P0's exit statement can change turn to 1. Since P0 is not interested in entering, P1 may wait indefinitely for an uninterested process. The entry decision therefore depends on a process outside the competition, violating Progress.

Step 4: Distinguish Progress from Bounded Waiting

Strict alternation bounds overtaking: after one process exits, it cannot enter again before the other takes its turn. The other process can therefore enter at most once before a requester receives permission. This is the bounded-waiting property used in the question.

However, a bound on the number of other entries does not ensure that an uninterested process will take its turn. The counterexample has no repeated overtaking at all; it fails because the waiting process cannot enter an unused critical section. Hence the defect is Progress, rather than option D's bounded-wait claim.

ProgressNoAn uninterested process can hold the turn while the critical section is empty.

Peterson's Solution

Peterson's Solution is a classic software solution to the Critical Section Problem for two processes. It combines the interest flags from the earlier array solution with a shared tie-breaker variable, favored.

The shared information is:

bool want[2] = {false, false};
int favored = 0;  // either 0 or 1 is a valid initial value

want[i] indicates whether process i wants to enter the critical section. When both processes are interested, favored decides which one receives priority. The standard theoretical analysis assumes atomic reads and writes of these variables, with memory operations observed in program order.

Algorithm for Process 0

while (true) {
    want[0] = true;
    favored = 1;

    while (want[1] && favored == 1);

    // critical section

    want[0] = false;
    // remainder section
}

P0 first sets want[0] = true to announce, “I want to enter.” It then sets favored = 1, politely giving priority to P1 if both processes are competing.

The waiting condition uses AND: P0 waits only while P1 wants to enter and P1 is favored. If either condition is false, P0 crosses the loop and enters. After finishing, it clears its own flag with want[0] = false.

Algorithm for Process 1

while (true) {
    want[1] = true;
    favored = 0;

    while (want[0] && favored == 0);

    // critical section

    want[1] = false;
    // remainder section
}

P1 behaves symmetrically. It announces interest, gives priority to P0, and waits only while P0 is interested and favored. The semicolon after each inner while makes it an empty busy-wait loop.

Case 1: Only One Process Wants to Enter

Suppose only P0 wants to enter. After its entry assignments, the state is:

want[0] = true
want[1] = false
favored = 1

P0 checks: want[1] && favored == 1
           false   && true
           = false

P0 enters immediately because P1 is not interested. This fixes Strict Alternation's Progress failure: a process does not have to wait for an uninterested process merely because that process is favored.

Case 2: Both Processes Want to Enter

Consider the following interleaving:

P0: want[0] = true;
P1: want[1] = true;
P0: favored = 1;
P1: favored = 0;    // last write: P0 receives priority

Both flags are true, and the final value of favored is 0. The waiting conditions become:

P0: want[1] && favored == 1
    true    && false = false   // P0 enters

P1: want[0] && favored == 0
    true    && true  = true    // P1 waits

Only P0 enters. When it finishes, it sets want[0] = false, making P1's waiting condition false so that P1 can proceed.

If the order of the writes is reversed, P1 writes favored = 0 first and P0 writes favored = 1 last. P1 then receives priority and P0 waits.

When both processes compete, the process that writes favored last gives priority to the other process. The tie-breaker resolves the conflict that caused deadlock in the flags-only solution.

Why All Three Requirements Are Satisfied

Mutual Exclusion — Yes. If both processes are interested, favored has only one value, so one waiting condition is true and the other is false. An entering process keeps its interest flag true throughout its critical section. If the other process attempts entry during that time, it gives priority to the process inside and must wait.

Progress — Yes. If only one process is interested, the other flag is false and entry is allowed. If both are interested, the tie-breaker permits one to proceed. An uninterested process cannot block entry, and both interested processes cannot remain stuck waiting for each other.

Bounded Waiting — Yes. Once a process has raised its flag and assigned favored, the other process can enter at most once before it. If the other process tries to re-enter, it must assign priority to the waiting process; because the waiting process's flag remains true, the re-entering process must wait. Thus, one process cannot repeatedly overtake the other. As usual, processes must continue to receive CPU time and finish their critical sections.

How to Remember It

want[i] = true;   // I want to enter.
favored = j;      // If you also want to enter, you go first.

while (want[j] && favored == j);
// Wait only while you are both interested and favored.

Here, j is the other process, so j = 1 - i. Peterson's Solution combines interest flags + a tie-breaker to satisfy Mutual Exclusion, Progress, and Bounded Waiting under the stated assumptions.

04

Hardware Solutions

Hardware Interrupts

One hardware-based approach to the Critical Section Problem on a single-processor system is to temporarily disable interrupts while executing a critical section. This prevents interrupt-driven preemption from handing the CPU to another process in the middle of a shared-data operation.

Why This Works on a Single CPU

On a single CPU, only one process can execute at any instant. An interrupt, such as a timer interrupt, transfers control to the operating system, which may perform a context switch and schedule another process. An interrupt does not always cause a context switch, but it provides a way for the OS to regain control.

Preemption means forcibly stopping the currently running process so another can use the CPU. If the kernel disables the relevant interrupts before a short critical section, interrupt-driven preemption cannot occur during that section. Provided the code does not block, yield, or otherwise invoke the scheduler, another process cannot run on that CPU and interfere with the shared data.

Example: Protecting an Increment

Consider the shared-variable operation:

x = x + 1;

This may involve separate read, modify, and write instructions. Without protection, the CPU could switch to another process between those instructions, allowing an update to be lost. Disabling interrupts around the sequence prevents that interrupt-driven switch on a single processor:

disable interrupts

LOAD  R1, x
ADD   R1, 1
STORE x, R1

enable interrupts

The current process completes the entire sequence before normal interrupt handling resumes. Other processes do not get CPU time in the middle, so they cannot modify x during that interval. The sequence behaves as a protected operation with respect to those processes, even though it still consists of multiple instructions.

Practical Limitations

It is a privileged kernel mechanism. Ordinary user programs should not be allowed to disable interrupts. A program that disabled them and never restored them could prevent normal timer handling and scheduling, leaving the system unresponsive.

It is insufficient on a multiprocessor system. Disabling interrupts on one CPU only affects that CPU. Another CPU can continue executing a process and accessing the same shared memory, so additional synchronisation, such as a suitable lock, is needed.

Critical sections must be short and must not block. Delaying interrupts increases interrupt latency and postpones time-sensitive work. Code must not sleep or yield while relying on interrupt disabling for protection.

The previous interrupt state must be restored. The example uses “enable interrupts” for simplicity. Real kernel code typically saves the previous state and restores it on exit, so it does not accidentally enable interrupts that were already disabled by its caller.

What to Remember

On a single processor, temporarily disabling interrupts can provide mutual exclusion for a short, non-blocking kernel critical section by preventing interrupt-driven preemption. It is a low-level mechanism with practical restrictions, and disabling interrupts on one CPU does not protect shared data from other CPUs.

Disabling interrupts is not a practical general-purpose synchronisation solution. On a single CPU, it can prevent interrupt-driven preemption so that the running process completes a short critical section safely, but on a multiprocessor system, disabling interrupts on CPU1 leaves CPU2, CPU3, and other processors running: CPU2 may still access the shared variable x while CPU1 modifies it, so a race condition remains possible. Trying to extend this approach across processors would require coordinating their execution through interprocessor messages or signals, introducing communication overhead whenever global protection is needed; merely disabling interrupts on every CPU would still not stop those CPUs from executing their current code, so additional coordination would be essential. Long periods with interrupts disabled can also delay timer interrupts used for scheduling and timekeeping, postponing clock updates and other time-sensitive OS activities. Ordinary user processes cannot safely be given this power: if buggy or malicious code disables interrupts and never restores them, timer and I/O interrupt handling may be disrupted and the system may become unresponsive. For this reason, interrupt disabling is generally a privileged kernel operation, useful only in carefully controlled, very short critical sections. The key GATE point is that disabling interrupts prevents preemption locally on a single CPU; it does not, by itself, provide global mutual exclusion across multiple CPUs.
