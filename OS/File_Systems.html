01

Introduction to File System

A file system provides the rules and data structures used to organise, store, name, and retrieve files on a storage device. It connects the files users see with their stored data and descriptive information.

The slide highlights three basic responsibilities: storing file contents, naming files, and storing file metadata.

1. Provides a Way to Store Files

A file system organises storage space, allocates space to files, and tracks where their contents are stored. A file's data may occupy multiple storage blocks; those blocks need not be adjacent.

Example: For files f1, f2, …, f100, the system must track which storage locations belong to each file so it can read or update the correct contents.

2. Provides a Way to Name Files

Names and directories let users identify files without knowing their physical storage locations. The file system resolves a name or path to the corresponding file information.

Example: A path such as /notes/os.txt identifies a file in a directory. The user can open it by name rather than specifying its storage blocks.

3. Provides a Way to Store File Metadata

Metadata is information about a file, rather than the file's contents. The exact attributes and their storage depend on the file system.

Metadata examplePurpose
File sizeRecords the length of the file.
Owner and permissionsIdentify ownership and control access.
TimestampsRecord events such as modification or access.
Storage-location informationHelps locate the blocks containing the file's data.

Data vs. metadata: The text inside os.txt is file data. Its size, permissions, and modification time are metadata. Names are also descriptive information, but may be stored in directory entries rather than in the file's own metadata record.

02

Disk Sectors and Blocks

A disk is divided into fixed-size sectors, numbered 0, 1, 2, …. A sector is a device-level storage unit; a file-system block is generally the unit managed by the file system and may contain one or more sectors.

Example: Using the question's binary convention, a 1 MB disk means 220 bytes (1 MiB). With 512-byte sectors:

Number of sectors = 220 / 512 = 2048   (numbered 0–2047)

Disk I/O is block-oriented: when an uncached read needs one byte from a 512-byte sector, the device transfers at least that sector into memory. The CPU can then access the required byte. Similarly, a 4 KiB block-level read transfers a whole block even if only a few bytes are needed.

Example: With 512-byte sectors and 4096-byte (4 KiB) file-system blocks, each block contains 8 sectors. If one byte in sector 3 of block 0 is needed and is not cached, a typical file-system read brings the entire block (sectors 0–7) into RAM. The CPU then accesses that byte.

Hardware vs. file system: the device addresses logical sectors, while file systems commonly read and cache data in blocks. A 4 KiB block request can transfer eight 512-byte sectors; reading the whole file-system block is typical behaviour, not a hardware requirement. The OS may instead request an individual logical sector.

Transfer unit vs. atomicity: treating a sector or block as a complete transfer unit does not guarantee that a write is indivisible during a power failure. Write atomicity is a separate property. Disk I/O is block-oriented, while main memory is byte-addressable.

Disk Layout: Metadata and File Data

Metadata describes files, including their sizes, permissions, and data locations. File data is their actual content, such as text, images, or program bytes.

The positions shown are illustrative. Real file systems may distribute metadata and file data across the device; metadata is not always confined to the first two sectors.

03

File System Layout

A file system must organise both file contents and the information needed to manage them. A simplified traditional Unix-style layout has four regions: a boot block, a superblock, an inode list, and data blocks.

1. Boot Block: Bootstrapping Information

A boot block is a reserved region that may contain bootstrap code used during startup to help load the operating system. Whether it is used depends on the boot arrangement; a file system used only for data need not contain active boot code.

2. Superblock: Information About the Whole File System

The superblock stores file-system-wide metadata, such as the file system's size, block size, block and inode counts, and information needed to locate or manage free-space structures. The exact fields depend on the implementation.

Think of it as the file system's overall information record, rather than the record of any one file.

3. Inode List: Information About Individual Files

In an inode-based file system, each file or directory is represented by an inode (index node). An inode records attributes such as size, owner, permissions, timestamps, and information for locating its data blocks. The inode list or table holds these records.

The file name is normally not stored in the inode. A directory entry maps a name to an inode number. The inode then identifies the file's metadata and data locations.

Some traditional file systems reserve a fixed inode table when created. They can run out of inodes even while data space remains free. Other file systems organise or allocate these records differently.

4. Data Blocks: File and Directory Contents

Data blocks hold the actual contents: text in a document, image bytes in a photo, or instructions in a program file. They also hold directory contents, including name-to-inode mappings, in the traditional Unix-style model.

Thus, a directory's inode describes the directory, while its data blocks contain the entries naming its children.

Example: Locating notes.txt

Suppose notes.txt contains 10 KiB of text and the file-system block size is 4 KiB. Assume an ordinary file stored in full-sized blocks, without compression, sparse regions, or inline data.

Data blocks required = ⌈10 / 4⌉ = 3 blocks

  1. The parent directory has an entry mapping notes.txt to its inode number.
  2. The inode records the 10 KiB file size and identifies the three data blocks. For example, these could be blocks 18, 41, and 70; they need not be consecutive.
  3. The blocks contain 4 KiB + 4 KiB + 2 KiB of file data. With full-block allocation, 2 KiB in the final block is unused.

Directory entry: name → inode number → inode → data blocks

ComponentMain purpose
Boot blockMay hold bootstrapping code.
SuperblockDescribes the entire file system.
Inode listHolds metadata records for individual files and directories.
Data blocksHold actual file and directory contents.

Keep the levels distinct: the superblock describes the file system, an inode describes a particular file, and data blocks contain its contents. The three-block calculation counts file data only, not additional directory or metadata storage.

04

Contiguous Allocation

Contiguous allocation stores all blocks of a file in consecutive disk block locations, without gaps. Instead of scattering the file across the disk, the file system reserves one continuous run of blocks.

Example: A.txt Occupies Three Consecutive Blocks

A disk has blocks numbered 0–9. File A.txt contains 12 KiB and each block holds 4 KiB:

Blocks required = ⌈12 / 4⌉ = 3

How Does the File System Locate a Block?

The allocation can be described using just the starting block and length in blocks. The file's byte size and other attributes are still maintained separately.

Disk block for file block i = start + i   (zero-based: 0 ≤ i < length)

For A.txt, the third file block has index i = 2, so its disk block number is 3 + 2 = 5. No chain of earlier blocks needs to be traversed.

Advantages and Limitations

Advantages

  • Efficient sequential access: successive file blocks are adjacent, reducing seeks on a hard disk.
  • Direct access: any file block's address is calculated from its index.
  • Small allocation metadata: one starting address and one length describe the run.

Limitations

  • External fragmentation: enough free blocks in total may exist without a sufficiently long consecutive run.
  • Difficult growth: extending the run requires adjacent free space; otherwise relocation or another allocation scheme may be needed.

Fragmentation example: free runs of lengths 3, 3, and 4 give 10 free blocks in total, but cannot hold a contiguous 5-block file. As with other block-based methods, a partly used final block may also waste space internally.

Why Not Put Another File in the Unused Bytes?

Assume the allocation unit is a 512-byte block (one sector here). In the basic model, each file receives whole blocks, even if its contents use only part of the last block:

BlockFile dataUnused space
0File A: 400 bytes512 − 400 = 112 bytes
1File B: 100 bytes512 − 100 = 412 bytes

Although 400 + 100 = 500 bytes could fit in one block, block 0 is already allocated entirely to A. Its unused 112 bytes are internal fragmentation, not a free block available to B. Sharing would require additional bookkeeping for sub-block ownership and updates.

Both kinds can occur: external fragmentation is free space split between allocated runs; internal fragmentation is unused space inside an allocated block. Some file systems reduce internal waste using tail packing or sub-block allocation, but those are outside this simple model.

Remember: contiguous allocation means consecutive block locations, described by a start and a length. Address calculation is simple, but finding and extending an unbroken free run can be difficult.

Extent-Based Allocation

An extent is a consecutive run of disk blocks allocated to a file. Extent-based allocation lets a file occupy one or more extents: blocks within an extent are consecutive, but different extents need not be adjacent.

Example: File A needs 8 blocks. Instead of requiring one 8-block run, allocate blocks 2–4 and 9–13:

Extent in file orderStarting disk blockLengthDisk blocks
123 blocks2, 3, 4
295 blocks9, 10, 11, 12, 13

Metadata describes these runs using start-and-length entries: here, just (2, 3) and (9, 5) represent all 8 data blocks. Larger implementations may index extents in a tree rather than a small array.

Easier growth: if the block after an existing extent is occupied, allocate another free run elsewhere and add an extent entry. The whole file need not be relocated. Long runs also need fewer address entries than listing each block separately.

Contiguous allocation: one continuous run per file. Extent-based allocation: multiple continuous runs per file. External fragmentation can still make large extents difficult to find, but the entire file no longer needs one unbroken region.

Question: What Is an Extent?

An extent in an extent-based file system is:

  1. A single contiguous block of fixed size
  2. A contiguous group of blocks allocated together
  3. A linked list node pointing to the next block
  4. A block that stores file metadata only

Correct answer: B. An extent is a consecutive run of blocks allocated together, described by its starting block and length. Its length can vary; it is not restricted to one fixed-size block. Keeping blocks together supports efficient sequential access, though external fragmentation can still occur.

05

Linked Allocation

Linked allocation lets a file's blocks occupy any free locations on disk. Each block stores file data and a pointer to the next block; the last has an end-of-chain marker, shown as NULL. The pointers determine logical order, not physical position.

Example: File A

File A's logical blocks B1, B2, and B3 are stored at disk blocks 3, 6, and 1. Starting at block 3, follow each next-block pointer:

B1: Disk 3
Next = 6
→
B2: Disk 6
Next = 1
→
B3: Disk 1
Next = NULL

The file record keeps its starting block; some implementations also keep the last block for appending. In basic linked allocation, pointers are stored inside the file's blocks:

Usable data per block = 4096-byte block − 4-byte pointer = 4092 bytes

Benefits: no external fragmentation and easy growth by linking another free block. Costs: pointer overhead, potentially scattered disk reads, and a broken pointer can make the rest of the chain inaccessible.

Sequential access follows the chain naturally. Random access is inefficient: without cached location information, finding the 100th block requires following the preceding 99 links. A partly used final block may still waste space internally.

Question: Total Pointer Overhead

Assume block numbers start from 0. In a linked file allocation system, each block stores 4 KB of data plus a 4-byte pointer to the next block. A file contains 1000 blocks. What is the total pointer overhead?

  1. 4 KB
  2. 4 MB
  3. 4000 bytes
  4. 4000 KB

Solution: Each of the 1000 blocks reserves one 4-byte pointer field, including the final block, whose field stores the end-of-chain marker.

Pointer overhead = 1000 × 4 bytes = 4000 bytes

Correct answer: C. Block numbering and data size do not change the pointer count. Here the pointer is additional to the stated data capacity, unlike the earlier fixed-total-block-size example. Under the common binary convention, 4 KiB is 4096 bytes; 4000 bytes is the exact answer requested.

FAT — File Allocation Table

FAT is a variation of linked allocation that moves next-block pointers out of the data blocks and into a separate table. A directory entry identifies the file's starting cluster; following FAT entries reveals the rest of its chain.

A cluster is FAT's allocation unit and consists of one or more sectors. The following teaching examples use block/cluster numbers interchangeably. Real FAT formats reserve some entries and marker values; the small numbers here are illustrative.

Read FAT[2] = 5 as “after cluster 2, go to cluster 5.” FAT stores links and allocation markers, not file names. For another independent example, FAT[2] = 5, FAT[5] = 6, and FAT[6] = EOF describe the chain 2 → 5 → 6 → EOF.

Does FAT Remove Pointer Chasing?

No: the chain still needs traversal. The improvement is that the FAT, or relevant parts of it, can be cached in RAM. To find B4, follow the links in memory, then read only its data cluster from disk.

Basic linked allocation

Read B1 to locate B2, B2 to locate B3, B3 to locate B4, then read B4's data.

4 data-block reads

FAT with links in memory

Traverse FAT entries in RAM to locate B4, then read B4's data. Earlier data blocks need not be read.

The two-read answer is conditional. A FAT may span many disk blocks; fetching all needed entries can require several reads. Count directory lookup separately if it is not already cached or excluded. Cached FAT improves disk I/O, but does not turn linked traversal into constant-time indexed access.

FAT Entry Size and Trade-offs

A 16-bit entry occupies 2 bytes and can encode a next-cluster number or a special marker such as free or end-of-chain. Some values are reserved, so not every bit pattern represents a usable data cluster.

Size of one FAT copy = number of entries × bytes per entry

Example: 1000 entries × 2 bytes = 2000 bytes. Count all table entries specified by the question; multiple FAT copies require additional space.

FAT avoids external fragmentation and supports growth by appending free clusters. Links no longer consume space inside each data cluster, but the separate table uses disk space and its cache uses RAM. A partially filled final cluster can still cause internal fragmentation.

Key distinction: basic linked allocation finds the next address inside a data block; FAT finds it in a separate table, preferably cached in memory. FAT is still linked allocation, not an index listing every file block by logical position.

Question: Find the Complete FAT Chain

Consider the following FAT table. The directory entry gives File A's starting block as 0. What is the complete block chain of File A?

Index01234567
Value57EOF124EOF6
  1. 0 → 5 → 4 → 2 → EOF
  2. 0 → 5 → 4 → 2
  3. 0 → 5 → 4 → EOF
  4. 0 → 5 → 4 → 2 → 3 → EOF

Solution: Start at block 0 and use each FAT value as the next index: FAT[0] = 5, FAT[5] = 4, FAT[4] = 2, and FAT[2] = EOF. Stop at the end-of-chain marker.

File A: 0 → 5 → 4 → 2 → EOF

Correct answer: A. The file occupies four blocks: 0, 5, 4, and 2. EOF is a marker, not another block. Use the question's simplified numbering; block 0 is a valid starting block here.

Question: GATE CSE 1996 · Question 23

A file system with a one-level directory is implemented on a disk with a block size of 4K bytes. The disk is used as follows:

Disk blockContents
0File Allocation Table: one 8-bit entry per data block, storing the data-block address of the next block in a file.
1Directory: one 32-bit entry per file.
2Data-block 1.
3Data-block 2; and so on.
  1. What is the maximum possible number of files?
  2. What is the maximum possible file size in blocks?

Part (a): Directory capacity. Using K = 1024, the directory occupies 4096 bytes. Each entry occupies 32 bits = 4 bytes:

Maximum directory entries = 4096 / 4 = 1024 files

This counts file names the directory can represent. Reaching this limit assumes files may be empty; requiring a data block for every file would introduce a separate data-space limit.

Part (b): Data-block address capacity. An 8-bit next-block address has 28 possible values. Under the simplified model in which all values identify data blocks, one file can occupy the entire addressable data-block pool:

Maximum file size = 28 = 256 data blocks

The 4 KiB FAT can physically hold 4096 one-byte entries, but an 8-bit link cannot distinguish that many next-block addresses. The address width, not the FAT block's byte capacity, is the tighter limit here.

Why the supplied 254-block solution needs an extra assumption: subtracting the FAT and directory blocks from 256 assumes links address the same physical disk-block namespace. The question instead says data-block addresses and explicitly distinguishes disk block 2 from data-block 1. Thus, 256 is the simplified data-address capacity; 254 applies if two of the 256 address values are reserved for those physical metadata blocks. Reserved end-of-chain or other marker values can also reduce usable capacity, but their encoding is not specified here.

Question: Maximum Partition Size in a FAT Design

Consider a FAT file system where the disk is divided into M-byte blocks, and every FAT entry can store an N-bit block number. What is the maximum size of a disk partition that can be managed by such a FAT design?

Solution: An N-bit block number can represent 2N distinct block addresses. Each addressed block holds M bytes, so:

Maximum partition size = number of addressable blocks × block size

= 2N × M bytes

Example: N = 16 and M = 512 = 29 bytes give 216 × 29 = 225 bytes = 32 MiB.

Addressable capacity is not FAT table size. The answer is 2NM bytes under the question's simplified model. Reserved address values and file-system metadata can reduce usable file-data capacity. For a hypothetical table with 2N tightly packed N-bit entries, the table itself occupies 2NN / 8 bytes.

06

Indexed Allocation

Indexed allocation keeps the addresses of a file's data blocks in a separate index structure. In the basic model, each file has an index block containing one pointer per data block. The data blocks can be anywhere on disk.

Unlike linked allocation, the data blocks do not form a next-block chain. The file's metadata identifies its index, and the index entries determine the file's logical block order.

Index block vs. inode: they are not interchangeable terms. An inode stores file metadata and may contain direct pointers plus pointers to indirect index blocks. It need not directly list every data block of a large file.

Example: Scattered Blocks, Ordered Index

A file has four logical blocks B1–B4, stored at disk blocks 7, 2, 15, and 9. Its index lists those addresses in logical file order:

In basic linked allocation, reaching B4 requires following the chain B1 → B2 → B3 → B4. With a single-level index, select entry 4 directly. The index may need to be read first if it is not cached, but earlier file-data blocks need not be read.

The same rule applies to a three-block file at addresses 3, 8, and 1: its first, second, and third index entries contain 3, 8, and 1, respectively.

Benefits and Index Capacity

  • Direct and sequential access: look up the required logical block's index entry.
  • No external fragmentation: any free data blocks can be used; consecutive space is unnecessary.
  • Index overhead: storing pointers requires extra metadata space and may require additional I/O. A mostly empty index block can waste space for a small file.
  • Finite capacity: one index block holds only a limited number of pointers. Larger files need additional indexing structures.

Inode-based designs can combine direct pointers with single-, double-, and triple-indirect pointers, reaching data blocks through one or more index levels. These levels extend capacity rather than enlarging the inode without limit.
