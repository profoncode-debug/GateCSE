Process, System Calls & CPU Scheduling

Detailed concepts, execution flows, distinctions, and exam-ready notes for GATE revision.

01

Program and Process

A program begins as source code written by a programmer. After compilation, it becomes an executable file on disk. When the Operating System loads that executable into main memory and begins its execution, it becomes a process.

Before compilation

prog.c is the source-code file. It contains the C instructions written by the programmer in a human-readable programming language.

After compilation

The compiler translates prog.c into a.out, an executable program containing machine-level instructions and stored on secondary storage such as a disk.

prog.c  →  Compiler  →  a.out

From Executable to Running Process

When the user runs a.out, the Operating System loads the executable into main memory (RAM).

The OS creates the required execution state and allows the CPU to begin executing the program's instructions.

At this stage, the passive executable has become an active process.

Source code
→
Compile
→
Executable
→
Load into RAM
→
Process

Program vs Process

Property Program Process
Meaning A set of instructions stored as an executable file. A program that has been loaded and is being executed.
Nature Passive Active
Location Normally stored on secondary storage such as a disk. Has an execution image in main memory and an associated execution state.

Remember: A program is a passive executable file on disk, whereas a process is an executing instance of that program.

02

CPU Execution and OS Control

The CPU does not execute only the instructions of a user program. It also executes Operating System instructions whenever the OS must manage the program, hardware, or another system event.

An illustrative instruction stream may contain several OS instructions, followed by instructions of Program A, and then more OS instructions:

OS → OS → OS → A → A → A → OS → …

Here, A represents instructions belonging to user Program A. The exact number of instructions executed during each interval can vary. OS instructions are required for loading programs, handling system calls and interrupts, scheduling processes, managing memory, and performing input/output operations.

Switching Control Between the OS and User Programs

The CPU executes one instruction stream at a time. Depending on events and scheduling decisions, control moves between Operating System code and user-program code.

Operating System code → User Program A → Operating System code → Another program

Key idea: The CPU executes whichever instruction the current control flow directs it to execute. The OS arranges and manages the execution of user programs, while OS code itself also runs as machine instructions on the same CPU.

What Happens After a Program Finishes?

After the last instruction of Program A executes, the CPU does not simply stop. Program termination returns control to the Operating System.

The OS records that Program A has terminated, performs the required cleanup, and may release or reclaim the resources associated with the completed process. The scheduler can then select another ready process and allow it to run.

Why Is an Operating System Required?

To understand the need for an Operating System, consider a computer on which no OS is installed. Suppose the following program is compiled into an executable file such as a.out:

int a = 1;
int b = 2;
int c = a + b;

Although this program is very small, the CPU cannot execute it directly from the disk without preparation. The program must be loaded into memory, the CPU must be directed to its first instruction, and the program must be given controlled access to hardware resources. Without an OS, the programmer would have to arrange all of this manually.

Program Loading and the Program Counter

Before execution can begin, the executable instructions must be loaded into RAM. The CPU must then know the memory address from which it should fetch the first instruction.

The Program Counter (PC) is a special CPU register that stores the memory address of the next instruction to be executed.

For example, if the first instruction of the program is loaded at address 1000, execution must begin with:

PC = 1000

The CPU fetches and executes the instruction at that address. The PC is then updated so that the CPU can fetch the next instruction in the sequence, unless an instruction changes the control flow.

Thus, two essential tasks must occur before execution:

  1. Load the executable program into main memory.
  2. Initialize the PC with the address of the appropriate first instruction, called the program's entry point.

Without an OS, these tasks would have to be performed manually whenever a program is run.

Remember: PC stands for Program Counter. It stores the address of the next instruction to be executed.

Interaction with Hardware

Consider a program containing printf("Hello");. The CPU and the monitor are separate hardware components, so the CPU cannot display the text merely by naming the monitor. The output must be sent through the appropriate hardware interface and device controller.

Direct hardware communication requires knowledge of device-specific details such as control registers, addresses, supported operations, communication protocols, and access permissions. Requiring every application programmer to manage these details would make even simple programs difficult to write and highly dependent on particular hardware.

The OS provides a convenient, controlled interface to hardware. A library function such as printf() ultimately requests an output service from the OS. The OS and the appropriate device driver translate that request into operations understood by the display hardware.

Application request → Operating System → Device driver → Hardware device

A device driver is system software that allows the OS to communicate with a particular type of hardware device. This arrangement hides device-specific implementation details from application programs.

Memory Management

When several programs are present in memory, their memory regions must be allocated and managed carefully. The system must decide where each program will be placed, how much memory it may use, and which addresses belong to it.

For example, suppose Program 1 occupies addresses 1000–1999 and Program 2 occupies addresses 2000–2999. If Program 2 incorrectly writes to address 1500, it may overwrite the instructions or data of Program 1.

The OS performs memory management by tracking the memory assigned to programs, allocating and reclaiming memory, and preventing unauthorized overlap or access. Without an OS, programmers would have to coordinate these memory locations manually.

Protection and Security

If programs could access every memory location and hardware device without restriction, one program could read or modify another program's data, corrupt important system memory, or issue unsafe hardware operations.

The OS establishes controlled execution environments using mechanisms such as:

  • Process isolation: separates the execution state of different processes.
  • Memory protection: restricts a process to memory that it is permitted to access.
  • Access permissions: control the use of files, devices, and other resources.
  • Privileged operations: reserve sensitive machine operations for trusted OS code.

The central requirement is that one program must not be allowed to arbitrarily read, modify, or damage another program or the Operating System.

Managing Multiple Programs

When several programs are ready to run, they compete for the CPU. A single CPU core normally executes only one instruction at a time, so the system must decide which process runs, when it runs, and how long it may continue before another process gets a turn.

This controlled sharing of the CPU is part of concurrency and resource management. The OS scheduler selects processes for execution and switches the CPU among them. The subject is studied in detail under CPU scheduling.

Time: P1   P1   P1  |  P2   P2  |  P1   P1  |  P3   P3  |  …

The illustrated order is only an example. The actual order depends on the scheduling policy and the state of each process.

Example: Concurrent Background Processes

#include <stdio.h>

int main(int argc, char *argv[]) {
    while (1) {
        printf("%s\n", argv[1]);
    }
    return 0;
}

The condition while (1) is always true, so the loop runs indefinitely. During every iteration, printf() prints the string stored in argv[1].

In the main() function:

  • argc stores the number of command-line arguments, including the program name.
  • argv is an array of strings containing those arguments.
  • argv[0] normally contains the name or path used to invoke the program.
  • argv[1] contains the first argument supplied after the program name.

For example, when the program is executed as ./prog A, the argument values are:

argv[0] = "./prog"    and    argv[1] = "A"

Therefore, this process repeatedly prints A.

Now consider running four instances:

./prog A & ./prog B & ./prog C & ./prog D

In a Unix-like shell, & requests background execution. Each invocation creates an independent process, so four processes are active and repeatedly attempt to print A, B, C, and D, respectively.

On a single CPU core, only one of these processes executes at a particular instant. The OS scheduler rapidly switches the CPU among the runnable processes, creating concurrent execution. Consequently, their output may be interleaved in the terminal, and an order such as A, C, B, D, ... is possible. No fixed output order is guaranteed because scheduling decisions can vary.

Safety condition: The program should be run with at least one command-line argument. Before using argv[1], robust code should verify that argc > 1; otherwise, passing the missing argument to printf("%s", ...) results in undefined behavior.

Common Tasks Performed by the OS

Without an OS, the following work would have to be repeated manually whenever programs are executed:

  1. Load the executable program into RAM.
  2. Identify the address of its first instruction.
  3. Initialize the Program Counter with that address.
  4. Arrange communication with hardware devices.
  5. Grant only the hardware access permitted to the program.
  6. Allocate memory to every program.
  7. Prevent programs from overwriting or reading one another's memory.
  8. Decide which process receives the CPU.
  9. Protect programs and the system from interference.
  10. Repeat the same setup and management for every program execution.

These tasks are common to almost all application programs; they are not part of the unique problem that each application is designed to solve. If no OS existed, every programmer would have to recreate much of the same loading, hardware-management, memory-management, scheduling, and protection infrastructure.

03

All About fork()

fork() is a Unix/Linux system call used to create a new child process from an existing parent process. Before fork(), only the parent exists. After fork(), there are two separate processes: the parent and the child. Both continue executing from the statement immediately after fork(), but they have different PIDs, their own CPU state, their own program counters/registers, and their own virtual address spaces. Logically, the child gets a copy of the parent’s memory, but the OS usually avoids copying all physical RAM immediately by using Copy-on-Write (COW): parent and child initially share the same physical memory pages for reading, and if either one writes to a shared page, the OS creates a separate physical copy for that process. Therefore, they remain independent even though some RAM may initially be shared. If RAM later becomes full, the OS may move process pages to swap space on secondary storage. These swapped pages are separate from the original executable file: the executable is the permanent program stored on disk, while swap contains temporary runtime memory pages belonging to processes. If both parent and child pages are swapped out, the OS stores them in separate swap locations and keeps track of which page belongs to which process.

Executable on disk
       |
       | run
       v
   Parent process
       |
     fork()
      / \
     /   \
 Parent   Child
   |        |
   └─ initially may share RAM pages ─┘
              |
        one process writes
              |
              v
      separate physical pages
              |
        if RAM is needed
              |

The key idea to remember is:

fork() creates a new independent process logically; Copy-on-Write makes that creation memory-efficient physically.

Question 1: Predict the Output

int main()
{
    int pid = fork();
    printf("%d\n", pid);
}

Solution: The fork() system call creates a new process. It returns different values to the parent and the child:

  • In the child process, fork() returns 0.
  • In the parent process, fork() returns the process ID (PID) of the child, which is a non-zero positive integer.

Therefore, the output will be two lines: 0 printed by the child and a non-zero integer printed by the parent. Either line may appear first.

Question 2: Output Printed by Parent and Child

int main()
{
    int pid = fork();

    if (pid == 0)
        printf("A");
    else
        printf("B");
}

Solution: The parent prints B and the child prints A. Their execution order is not guaranteed, so the combined output may be AB or BA.

Question 3: Address Printed by Parent and Child

Question: What is the output of the following code?

#include <stdio.h>
#include <unistd.h>

int main() {
    int a = 10;
    if (fork() == 0) {
        printf("%p", &a);
    } else {
        printf("%p", &a);
    }
}

Options:

  1. The parent and child print DIFFERENT addresses.
  2. The parent and child print SAME addresses.
  3. The child cannot access a, so no address is printed.
  4. The addresses printed depend on the scheduling order of the processes.

Solution: The correct answer is B. The parent and child print the same virtual address for a.

#include <stdio.h>
#include <unistd.h>

int main() {
    int a = 10;

    printf("Before fork: PID = %d, a = %d, &a = %p\n",
           getpid(), a, (void *)&a);

    int x = fork();

    if (x == 0) {
        a = 20;
        printf("Child: PID = %d, a = %d, &a = %p\n",
               getpid(), a, (void *)&a);
    } else {
        a = 30;
        printf("Parent: PID = %d, a = %d, &a = %p\n",
               getpid(), a, (void *)&a);
    }

    return 0;
}

This source code is first compiled into an executable program, and that executable is stored in secondary memory. When you run the executable, the operating system creates a parent process. That process gets a PID, its own virtual address space, stack, heap, program counter, register state, page table, and other process-related information. The variable a may appear to the parent at a virtual address such as 1000. That 1000 is not an actual RAM location; it is simply the address the parent process uses inside its own virtual address space. The MMU translates that virtual address using the parent's page table to some real physical RAM location, for example 5000, and the actual bytes representing the value of a are stored there. When fork() is executed, the operating system creates a child process. The child gets a different PID and its own process context, page table, virtual address space, stack, heap, and register state, but it initially inherits the same virtual memory layout as the parent. Therefore, the child may also see a at virtual address 1000. Initially, because of copy-on-write, the parent and child may even share the same physical RAM page. If either one modifies that memory, the operating system creates a separate physical copy for the process that writes. So after the parent changes a to 30 and the child changes a to 20, both may still see a at virtual address 1000, but the parent's 1000 may map to physical RAM location 5000, while the child's 1000 may map to physical RAM location 9000. Therefore, 1000 is not where the data physically sits in RAM; it is the process-visible virtual address, while 5000 and 9000 are example physical locations in RAM where the actual bytes are stored. If printf("%p", &a) is used, both processes can print the same virtual address because each process has its own separate virtual address space.

Question 4: Values and Addresses After fork()

Consider the following code fragment:

if (fork() == 0) {
    a = a + 5;
    printf("%d, %p\n", a, &a);
}
else {
    a = a - 5;
    printf("%d, %p\n", a, &a);
}

Let u, v be the values printed by the parent process and x, y be the values printed by the child process. Which one of the following is TRUE?

  1. u = x + 10 and v = y
  2. u = x + 10 and v != y
  3. u + 10 = x and v = y
  4. u + 10 = x and v != y

Solution: Suppose a has the value k before fork(). The parent prints u = k - 5, while the child prints x = k + 5. Thus, u + 10 = x. Parent and child have separate virtual address spaces with the same layout immediately after fork(), so the process-visible address of a is the same in both: v = y. Option C is correct. The order of the two printed lines can vary.

Question 5: Two Consecutive fork() Calls

int main() {
    fork();
    fork();
    printf("hello\n");
    exit(0);
}

Solution: The first fork() creates one child, giving 2 processes. Both execute the second fork(), giving 22 = 4 total processes. Each process eventually executes printf("hello\n"), so hello is printed four times.

Question 6: Possible Output with waitpid()

int main() {
    if (fork() == 0) {
        printf("a");
    } else {
        printf("b");
        waitpid(-1, NULL, 0);
    }
    printf("c");
    exit(0);
}

Solution: The possible output patterns listed in the notes are:

  • B A C C
  • A B C C
  • A C B C

The child's a comes before its c. The parent's final c comes after the child has finished because the parent calls waitpid(). The two processes can otherwise be scheduled in different orders.

Question 7: Child Processes from Three fork() Calls

How many child process will create?

for (i = 1; i <= 3; i++) {
    fork();
}

Solution: Three rounds of fork() result in 23 = 8 total processes, including the original process. Therefore, 23 - 1 = 7 child processes are created.

Question 8: Two fork() Calls in Each Iteration

How many child process will create?

for (i = 1; i <= 3; i++)
{
    fork();
    fork();
}

Solution: There are 6 total fork calls along each process path (2 forks per iteration for 3 iterations). The total number of processes is 26 = 64. The number of child processes is 26 - 1 = 63.

Question 9: Child Processes After n Iterations

A process executes the following code. The total number of child processes created is:

for (i = 0; i < n; i++)
    fork();
  1. n
  2. 2n - 1
  3. 2n
  4. 2n+1 - 1

Solution: Each iteration doubles the number of processes. Starting with one process, after n iterations there are 2n processes in total. Excluding the original process gives 2n - 1 child processes. Option B is correct.

Question 10: Negative Return Value of fork()

Statement: When fork() returns a negative integer, an error has occurred that must be dealt with in both the parent and child process.

Answer: False. When fork() returns a negative integer, an error has occurred, but no child process is actually created. Therefore, only the original process can handle the error.

Question 11: Conditional fork() Calls

Find the total number of processes created by the following code:

pid_t pid1, pid2;
pid1 = fork();
pid2 = fork();
if (pid1 > 0 && pid2 == 0) {
    if (fork())
        fork();
}

Solution: The first two fork() calls leave 4 processes. Only one of them—the child created by the second fork() in the original parent—has pid1 > 0 and pid2 == 0. That process executes if (fork()), creating one more child. The parent of that new child receives a nonzero return value and executes the final fork(), creating one more child. Thus, there are 4 + 1 + 1 = 6 processes in total, of which 5 are newly created child processes.

Question 12: printf() Before fork()

For the first code,

for (i = 1; i <= 3; i++) {
    printf("Hello");
    fork();
}

printf("Hello") executes before each fork(). In the first iteration only 1 process exists, so Hello is printed once; after the fork there are 2 processes. In the second iteration, those 2 processes each print Hello, giving 2 more prints, and then both fork to make 4 processes. In the third iteration, the 4 processes each print Hello, giving 4 more prints. Therefore, the total number of prints is 1 + 2 + 4 = 7.

Question 13: printf() After fork()

For the second code,

for (i = 1; i <= 3; i++) {
    fork();
    printf("Hello");
}

the fork() happens before the printf(). In the first iteration, 1 process forks into 2, so Hello is printed 2 times; in the second iteration, 2 processes fork into 4, so it is printed 4 times; in the third iteration, 4 processes fork into 8, so it is printed 8 times. Therefore, the total number of prints is 2 + 4 + 8 = 14. The key idea is that when printf() comes before fork(), it is executed by the processes that already exist at the start of that iteration, whereas when printf() comes after fork(), both the parent and newly created child execute it.

Question 14: continue and break After fork()

Consider the following program snippet. Assume that the program compiles and runs successfully. Further, assume that the fork() system call is always successful in creating a process.

int main() {
    int i;

    for (i = 0; i < 3; i++) {
        if (fork() == 0) {
            continue;
        }
        break;
    }

    printf("Hello!");
    return 0;
}

The total number of times that the printf statement gets executed is ____ (answer in integer).

Solution: Initially, one process enters the loop and executes fork(). The parent gets a positive return value, so fork() == 0 is false and it executes break, leaves the loop, and prints "Hello!"; the child gets 0, executes continue, and moves to the next iteration. In the second iteration, only that child executes another fork(); again its parent breaks and prints "Hello!", while its new child continues. In the third iteration, the same thing happens once more: the parent breaks and prints, while the newest child continues; after i becomes 3, that final child exits the loop normally and also prints "Hello!". Therefore, there are 4 processes reaching printf(), so the answer is 4.

04

All about exec

exec() is a Unix/Linux system call family used to replace the program that is currently running inside a process with another program. The most important point is that exec() does not create a new process. The process keeps the same identity, including the same PID, but the program code and most of the process memory image are replaced by the new executable. So if a process is currently running a.out and then successfully calls exec() to run b.out, the same process stops executing the code of a.out and starts executing the code of b.out. You can think of it as keeping the same process container but replacing what is running inside that container.

Suppose a.out contains code that first prints "hello", then calls exec() to run b.out, and then has another printf() statement after the exec() call. Once exec() succeeds, the old program a.out is replaced by b.out, so execution does not come back to the next line of a.out. That means the printf("I am back") statement will never execute. A successful exec() effectively says, “from this point onward, this process is now running the new program.” Only if exec() fails would control return to the old program.

A simplified version of a.out can be written like this:

#include <stdio.h>
#include <unistd.h>

int main() {
    printf("hello\n");

    execl("./b.out", "b.out", NULL);

    printf("I am back\n");   // executes only if exec fails

    return 0;
}

Here, execl() is one member of the exec family. The first argument tells the OS which executable to run. After execl("./b.out", ...) succeeds, the process no longer continues with the remaining code of a.out. Instead, the process starts executing b.out.

Now suppose b.out was produced from this program:

#include <stdio.h>

int main() {
    printf("hey, it is b\n");

    return 0;
}

When a.out is executed, the process first prints "hello". Then exec() replaces a.out with b.out, and the same process begins executing b.out, which prints "hey, it is b". Therefore, the output is approximately:

hello
hey, it is b

The line "I am back" is not printed because exec() does not behave like a normal function call that returns after the new program finishes. It replaces the old program entirely. The PID can remain the same because no new process has been created; only the program running inside that process has changed. This is the major difference between fork() and exec(): fork() creates a new child process, while exec() keeps the existing process and replaces its current program with another executable. In real Unix systems, these two are commonly used together: a parent calls fork() to create a child, and the child then calls exec() to run a different program.

When you type ./a.out in a terminal, the shell process does not replace itself with a.out; instead, the shell first calls fork() to create a child process, so there are temporarily two processes: the original parent shell and a child that initially looks like the shell. The child then calls exec("./a.out"), which replaces the child’s current program with a.out while keeping the same child PID. The parent shell usually waits while a.out runs, and when a.out finishes, the child process terminates and the shell becomes active again and shows the prompt. So the key idea is: fork() creates a new process, while exec() replaces the program running inside that process.

05

Kernel and system calls

The kernel is the core and most privileged part of an operating system. It manages important system resources such as the CPU, memory, files, devices, and processes. Normal applications do not get direct unrestricted access to these resources, because that would make the system unsafe. Instead, the CPU operates using different privilege levels, mainly user mode and kernel mode. Normal programs such as browsers, editors, and C programs execute in user mode, where their privileges are restricted. The operating system kernel executes in kernel mode, where it can perform privileged operations and directly manage hardware and protected memory.

A system call is the mechanism through which a program running in user mode requests a service from the operating system kernel. For example, operations such as reading a file, writing output, creating a process, or waiting for another process require help from the OS. Common system calls include read(), write(), open(), close(), fork(), exec(), and wait(). A simple computation such as a = b + c does not require a system call because the CPU can perform it directly in user mode.

When a system call occurs, execution must temporarily move from user mode to kernel mode. In the common textbook convention, the CPU maintains a mode bit, where 1 represents user mode and 0 represents kernel mode. While the user program is executing, the mode bit is 1. When the program requests a system service, a special CPU mechanism such as a trap or software interrupt transfers control to the kernel and changes the mode to kernel mode. The kernel then performs the requested operation. After the operation is completed, control returns to the user process and the CPU switches back to user mode. Therefore, the basic sequence is:

User mode
   ↓
System call
   ↓
Trap / software interrupt
   ↓
Kernel mode
   ↓
Execute requested service
   ↓
Return
   ↓
User mode

A trap in this context should not be thought of as an error. It is a controlled mechanism by which the CPU safely transfers execution from user code to kernel code. A user process cannot simply jump into the kernel using an ordinary function call because kernel code is protected and executes with greater privilege. The special trap or system-call instruction ensures that this transition happens safely.

It is also important to distinguish between a library call and a system call. A library call is simply a function supplied by a software library. It may or may not invoke a system call. For example, strlen() or strcpy() can perform their work entirely in user memory, so they normally do not need a system call. On the other hand, some library functions eventually need services from the operating system and therefore invoke system calls.

printf() is a very important example. printf() is not itself a system call; it is a C standard library function. It performs tasks such as formatting and buffering the output. When the output actually needs to be sent to a terminal or file, the library may eventually use the write() system call. So the conceptual path can be written as:

printf()
   ↓
C standard library
   ↓
write()
   ↓
System call mechanism
   ↓
Kernel

This also explains the idea of an API, or Application Programming Interface. An API is a set of functions and other programming facilities that applications use to perform common operations. User programs usually interact with these convenient functions rather than dealing directly with low-level kernel mechanisms. Some API functions require no system call, some are almost direct wrappers around system calls, and some perform additional work before eventually invoking one. For example, strcpy() generally uses no system call, write() closely corresponds to a system call, and printf() performs formatting and buffering before possibly using write().

So the complete picture is:

Application / User Program
          ↓
API / Library Function
          ↓
may require a System Call
          ↓
Trap / special CPU instruction
          ↓
Kernel Mode
          ↓
Operating System performs service
          ↓
Return to User Mode

The kernel is the privileged core of the OS; user mode is restricted while kernel mode is privileged; a system call is a request from a user program to the kernel; a system call causes a controlled user-mode-to-kernel-mode transition; and not every library/API function is a system call. In particular, remember: printf() is a library function, while write() is a system call.

Inside a system call, a library wrapper such as write() prepares the arguments and a system call number, usually placing them in CPU registers, then executes a special instruction such as syscall. This transfers control from user mode to kernel mode through a protected entry point. The CPU and kernel preserve the user process state needed to resume it, including its execution position and stack context; the PC (Program Counter) identifies the next instruction to execute, and the SP (Stack Pointer) identifies the current stack position. Execution moves to a protected kernel stack and the kernel's system call handler. The handler uses the system call number to find the appropriate service routine in the system call table, which maps call numbers to kernel functions and prevents applications from entering arbitrary kernel code. The selected routine checks the request, performs the operation, and places a result or error indication where the user program can receive it. The saved state is then restored and execution returns to user mode after the system call. The numeric encoding of user and kernel privilege depends on the architecture; the essential transition is from restricted user mode into privileged kernel mode and back. A system call costs more than an ordinary function call because it involves this controlled transition, state saving and restoration, kernel work, and often stack switching or other hardware effects. To reduce repeated system calls when practical, libraries may buffer output: printf() can collect characters and send them with fewer, larger write() calls.

06

Threads

A process is a program that is currently executing, and it contains the program code, data section, heap, stack, and the resources required for execution. To manage each process, the operating system maintains a Process Control Block (PCB), which is a kernel data structure stored in kernel memory. The PCB contains important information about the process such as its Process ID (PID), current process state, program counter, CPU registers, scheduling information, memory-management information, open files, and other resource details. The actual code, heap, and stack are part of the process itself, while the PCB only stores the information needed by the OS to control, schedule, stop, and later resume that process.

Threads of the same process share its address space, program code, static data, and heap. They do not share their program counters, CPU register states, or stack spaces: each thread has its own PC showing where it is executing, its own registers (including a stack pointer), and its own stack for function calls and local variables. The separate stacks still lie within the process's shared virtual address space.

In a multithreaded process, all threads share the same code, data, heap, and open files, but each thread has its own stack, registers, program counter, and stack pointer. Because each thread has a separate stack, a local variable stored in one thread’s stack is normally private to that thread. For example, if a is a local variable in Thread T2’s stack, then Thread T1 cannot directly access a as its own local variable. However, since all threads belong to the same process and therefore share the same virtual address space, T1 can indirectly access a if it somehow gets the address of a, for example through a pointer. So the key idea is: stack is private logically, but the memory is still inside the same process address space, so another thread can access it if it knows the address.

Creating a process is the most expensive because the OS must set up a separate process with its own address-space-related structures and other process resources. Creating a kernel-level thread is cheaper because threads of the same process share resources such as code, data, heap, and open files, but the kernel still has to create and manage the thread, so there is system-call and scheduling overhead. User-level threads are usually the cheapest and fastest to create or switch because they are managed in user space by a thread library with little or no kernel involvement. Hence, in terms of overhead, the general order is Process > Kernel-level thread > User-level thread.

Thread Mapping Models

In the many-to-one model, many user-level threads such as U1, U2, and U3 are mapped onto a single kernel thread K1. The important point is that the kernel does not know about U1, U2, or U3 individually; it only knows about K1. The OS scheduler gives CPU time to K1, and then the user-level thread library inside the process decides which user thread will use that CPU time. So the thread library may run U1 for some time and then switch to U2, while the kernel still sees only the same K1. Because all user threads depend on one kernel thread, if one user thread makes a blocking system call and K1 gets blocked, then the entire process effectively stops, since the other user threads have no other kernel thread through which they can execute. Also, true parallel execution on multiple CPUs is not possible because there is only one kernel thread.

In the one-to-one model, every user-level thread is mapped to its own kernel thread, for example U1 → K1, U2 → K2, and U3 → K3. Here the kernel knows each kernel thread separately and can schedule them independently. Therefore, if one thread blocks, the others can still continue running. Also, on a multicore system, K1, K2, and K3 can be scheduled on different CPU cores at the same time, giving true parallelism. The disadvantage is that creating and managing many kernel threads is more expensive because the kernel has to maintain each one separately.

In the many-to-many model, many user-level threads are mapped onto multiple kernel threads. For example, a process may have U1, U2, U3, U4, U5 but only K1 and K2. The user-level thread library decides which user thread will run on an available kernel thread, while the kernel schedules only the kernel threads onto CPUs. This gives more flexibility than many-to-one because if one kernel thread blocks, other user threads may still run through another kernel thread. It also allows parallel execution because multiple kernel threads can run on different CPUs. At the same time, it can use fewer kernel threads than the total number of user threads, reducing kernel overhead compared with one-to-one.

So the core idea of mapping is simply: which kernel thread is used to carry the execution of a user thread to the CPU. In many-to-one, the kernel sees only one thread; in one-to-one, each user thread has its own kernel thread; and in many-to-many, many user threads share a pool of multiple kernel threads.

Introduction to CPU Scheduling

A process state diagram shows the different stages through which a process passes during its lifetime. A process does not remain in one condition from start to finish. Sometimes it is being created, sometimes it is waiting for the CPU, sometimes it is actually executing, sometimes it is waiting for an I/O operation to finish, and finally it terminates. The OS keeps track of these changes in the PCB (Process Control Block) of the process. So whenever we say that a process changes state, internally the OS updates the state information in its PCB and manages that process accordingly.

The first state is the New state. When a user or another process requests the OS to create a new process, the process initially enters this state. At this stage, the process is not yet ready to run. The operating system is still setting it up. It may create the PCB, assign a process ID, create the process address space, load the program code, initialize registers, allocate required memory, and set up other resources. Once all the necessary setup has been completed and the OS is willing to allow the process to compete for CPU time, the process moves from New to Ready. So the New state essentially means, “the process is currently being created.”

The Ready state means that the process has been created successfully and is fully capable of executing, but it is not currently getting the CPU. This distinction is very important. A process in the Ready state is not blocked by I/O or some event. It has everything it needs except access to the processor. In a system, many processes can be in the Ready state at the same time. These ready processes are usually organized in a structure called the Ready Queue. The CPU scheduler examines this set of ready processes and chooses one of them to execute. So when we study scheduling algorithms such as FCFS, SJF, SRTF, Priority Scheduling, and Round Robin, we are mainly studying the different rules used to decide which process from the Ready Queue should be selected next.

When a process is selected by the scheduler, it moves from the Ready state to the Running state. In the Running state, the CPU is actually executing the instructions of that process. On a single-core processor, only one process can truly be in the Running state at a particular instant, although many other processes may be waiting in the Ready Queue. On a multicore processor, multiple processes can be running simultaneously, with each core executing one process or thread. The transition from Ready to Running is therefore one of the most important transitions in CPU scheduling because this is where the scheduler decides who gets the processor.

A process does not necessarily continue running until it finishes. While it is in the Running state, several things can happen. The simplest possibility is that the process completes all of its instructions. In that case, it moves from Running to Exit, also called the Terminated state. At this point, the process has finished execution. The operating system can then release resources that were associated with the process, such as memory, open files, and other kernel resources. Eventually the process entry itself is cleaned up after any required termination information has been collected.

Another possibility is that a running process requests an I/O operation or needs to wait for some event. For example, suppose a process asks the disk to read a file, waits for keyboard input, requests data from the network, or waits for a resource to become available. The CPU cannot continue executing the process meaningfully until that required event occurs. Therefore, the OS moves the process from the Running state to the Waiting state. This state is also commonly called the Blocked state. A Waiting process is fundamentally different from a Ready process. A Ready process can execute immediately if it is given the CPU, whereas a Waiting process cannot execute even if you give it the CPU because the thing it is waiting for has not happened yet.

For example, imagine process P1 is currently running and suddenly requests data from the disk. Disk access is much slower than CPU execution. If the CPU simply waited idly for the disk to respond, a lot of CPU time would be wasted. Instead, the OS puts P1 into the Waiting state and allows some other process, say P2, from the Ready Queue to use the CPU. This is one of the main reasons multiprogramming improves CPU utilization. While one process is waiting for I/O, another process can make productive use of the processor.

Once the event that the process was waiting for has completed, the process moves from the Waiting state back to the Ready state. For example, if P1 was waiting for disk data and the disk operation finishes, P1 is now capable of continuing execution. However, it usually does not go directly from Waiting to Running because another process may already be using the CPU. Instead, P1 joins the Ready Queue again and waits for the CPU scheduler to select it. So the normal path is Waiting → Ready → Running, not directly Waiting → Running.

There is also another very important transition that is often present in the complete process-state diagram: Running to Ready. This transition occurs when the currently running process is forced to give up the CPU even though it has not finished and is not waiting for I/O. This is called preemption. For example, in Round Robin scheduling, each process is allowed to run for only a fixed amount of time called the time quantum. If the process does not finish within that time, the OS interrupts it, saves its current execution state in the PCB, moves it back to the Ready Queue, and gives the CPU to another process. The interrupted process can continue later from exactly where it stopped.

This Running-to-Ready transition is what separates many preemptive scheduling algorithms from non-preemptive ones. In non-preemptive scheduling, once a process gets the CPU, it usually keeps it until it either terminates or voluntarily blocks, for example by requesting I/O. In preemptive scheduling, the OS may take the CPU away from a running process. You will see this idea repeatedly when comparing algorithms such as SJF versus SRTF or FCFS versus Round Robin.

So the entire life cycle can be understood as follows. The process begins in New, where the OS is creating it. After creation, it goes to Ready, where it waits for CPU time. When selected by the scheduler, it becomes Running. From Running, it can either finish and move to Exit, request I/O and move to Waiting, or be preempted and return to Ready. If it enters Waiting, then when the awaited event or I/O completes, it returns to Ready and waits for the scheduler again.

The most important thing to remember for scheduling is the difference among Ready, Running, and Waiting. A process in Ready wants the CPU and can run immediately if selected. A process in Running currently has the CPU. A process in Waiting is not competing for the CPU because it cannot proceed until some external event or I/O completes. Therefore, CPU scheduling algorithms mainly operate on the processes that are in the Ready Queue.

You can mentally summarize the whole diagram like this:

New means being created, Ready means waiting for CPU, Running means using CPU, Waiting means waiting for some event or I/O, and Exit means finished.

And the key scheduling idea is:

Ready → Running is decided by the CPU scheduler. Running → Ready happens because of preemption. Running → Waiting happens because the process needs something such as I/O. Waiting → Ready happens when that event finishes.

Scheduling Time Terms

  • Arrival Time (AT): The time at which a process enters the ready queue and becomes available for CPU scheduling. Example: if P1 becomes ready at time 3, then AT = 3.
  • Burst Time (BT): The total amount of CPU execution time required by the process. It tells us how long the process needs the CPU to complete its current CPU burst. Example: if P1 needs 5 ms of CPU time, then BT = 5 ms.
  • Completion Time (CT): The time at which a process finishes its execution completely. Example: if P1 finishes at time 12, then CT = 12.
  • Turnaround Time (TAT): The total time a process spends in the system, from its arrival until its completion. TAT = CT − AT.
  • Waiting Time (WT): The total time a process spends waiting in the ready queue for the CPU. It does not include the time during which the process is actually executing on the CPU. In the standard scheduling problems we solve, WT = TAT − BT. This formula assumes there is no separate time spent blocked for I/O.

So the key formulas are:

TAT = CT − AT

WT = TAT − BT

For example, if a process has AT = 2, BT = 5, CT = 10, then:

TAT = 10 − 2 = 8

WT = 8 − 5 = 3

So the process was in the system for 8 units, out of which it used the CPU for 5 units and waited in the ready queue for 3 units.

FCFS (First-Come, First-Served)

In FCFS scheduling, the process that enters the ready queue first gets the CPU first. This is a non-preemptive algorithm: once selected, a process keeps the CPU until its CPU burst finishes or it blocks.

In FCFS (First Come, First Served), the two ideas are very different:

Convoy effect means that a long CPU-bound process at the front of the ready queue makes many short processes wait behind it. Since FCFS is non-preemptive, once the long process gets the CPU, the short processes cannot interrupt it. For example, if P1 needs 24 units of CPU time and P2 and P3 each need only 3 units, but P1 arrives first, then P2 and P3 must wait until P1 finishes. This increases the average waiting time and turnaround time. It is called the convoy effect because many short processes move behind one long process like vehicles stuck behind a slow truck.

Starvation, on the other hand, means that a process waits for an indefinitely long time because other processes keep getting selected before it. In normal FCFS, starvation does not occur because processes are served strictly in arrival order. Once a process enters the ready queue, every process ahead of it will eventually finish, and then its turn must come. New processes arriving later cannot jump ahead of it.

So for FCFS, remember:

Convoy effect: YES — a long process can delay many short processes.

Starvation: NO — every process eventually gets the CPU.

This is an important GATE point: FCFS may have poor waiting time because of convoy effect, but it is starvation-free.

SJF (Shortest Job First)

Shortest Job First (SJF) selects the ready process with the shortest next CPU burst. In its non-preemptive form, once a process starts running, it keeps the CPU until that burst finishes or it blocks. The scheduler compares only processes that have already arrived and are ready at the selection time.

Convoy effect: SJF reduces the usual FCFS convoy effect by choosing short jobs ahead of a long job when all are waiting in the ready queue. However, non-preemptive SJF cannot interrupt a long job that has already started, so short jobs arriving afterward may still be stuck behind it. Thus, long-job blocking is still possible.

Starvation: SJF can cause starvation of a long job if shorter jobs keep arriving and are always selected first.

Round Robin (RR)

Round Robin is a preemptive scheduling algorithm. Each ready process receives at most a fixed amount of CPU time called the time quantum. If its CPU burst is not finished when the quantum expires, the OS moves it to the back of the ready queue and gives the CPU to the next ready process.

Convoy effect: A short quantum limits how long short jobs wait behind one long CPU-bound job, so RR greatly reduces the classic FCFS convoy effect. A very large quantum makes RR behave more like FCFS, and convoy-like delays can then occur.

Starvation: Standard RR does not cause starvation. A ready process gets another turn after the processes ahead of it have each received at most one quantum, assuming normal finite scheduling overhead and that new arrivals join the back of the queue.

SRTF (Shortest Remaining Time First)

Shortest Remaining Time First (SRTF) is the preemptive form of SJF. At each scheduling decision, the ready process with the least CPU time remaining is selected. If a newly arrived process needs less time than the currently running process has left, the running process is preempted.

Convoy effect: SRTF avoids the classic FCFS convoy effect because an arriving short process can preempt a long process instead of waiting for its entire burst to finish.

Starvation: SRTF can starve a long process if shorter jobs keep arriving and repeatedly take priority.
