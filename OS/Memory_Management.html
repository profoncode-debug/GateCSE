Introduction

Base and Bound

Suppose a process is loaded in physical memory starting at address 5000, and its total size is 1000 bytes. The OS keeps two registers: the Base register = 5000, which tells where the process starts in physical memory, and the Bound/Limit register = 1000, which tells how large the process is.

Valid address

If the CPU generates logical address 300, hardware checks 300 < 1000. Since it is valid, the physical address becomes:

5000 + 300 = 5300

Invalid address

If the CPU generates 1200, it is outside the process's allowed range, so the hardware traps to the OS.

1200 ≥ 1000 → Trap

Base gives relocation; Bound gives protection.

For every running process, the operating system maintains two hardware registers called the base register and the bound register. The base register stores the starting physical address where the process is loaded in main memory, while the bound register stores the size of the process and therefore defines the valid range of logical addresses that the process can generate. Whenever the CPU generates a logical address, the hardware first checks whether it is smaller than the bound value. If it is valid, the physical address is calculated as Physical Address = Base Address + Logical Address; otherwise, the hardware generates a trap because the process is trying to access memory outside its permitted region. For example, if the base is 42000 and the bound is 3000, valid logical addresses range from 0 to 2999, which map to physical addresses 42000 to 44999.

Segmentation

In segmentation, instead of treating the whole process as one continuous block, we divide it according to its logical parts, such as code, data, stack, heap, etc. Each segment has its own base and bound. The segment table may look conceptually like this:

Segment numberLogical partBaseLimit (bytes)
0Code1000400
1Data5000200
2Stack9000300

A logical address is written as (segment number, offset). For example, (1, 120) means segment 1 with offset 120. We first check whether 120 < limit[1]; if yes, physical address = base[1] + 120.

120 < 200 → Physical address = 5000 + 120 = 5120

You can think of segmentation as multiple base-and-bound pairs, one for each segment.

Clarifying the Logical-to-Physical Mapping

In segmentation, a logical address is normally a pair (segment number, offset). The segment number selects an entry in the segment table. Its base gives the segment's starting physical address, and its bound gives the segment's size. The hardware checks that the segment number is valid and that 0 ≤ offset < bound[segment]. If the checks pass, it adds the offset to that segment's physical base; otherwise, it generates a trap.

(segment, offset) → Segment table → Physical address = base[segment] + offset

Each segment is contiguous in physical memory, but different segments of the same process can be placed in separate physical regions. Logical segment order does not require the same physical order. For example, in the table above, logical address (1, 120) selects the Data segment and maps to 5000 + 120 = 5120; it does not use the Code segment's base.

Practical Problems: External Fragmentation

It has some practical problems because each segment is variable-sized and must occupy a contiguous block of physical memory. As processes are loaded, removed, or their segments grow, free memory gets broken into many small scattered holes, producing external fragmentation. Even if the total free memory is large enough, there may not be one sufficiently large contiguous block for a new or expanding segment. To solve this, the OS may need to relocate segments or compact memory, which means moving large amounts of data and is time-consuming; similarly, swapping an entire process between RAM and secondary storage also takes time. This same external-fragmentation problem also appears in simple base-and-bound schemes because there too, each process needs a contiguous region of physical memory.

Paging

Paging is different. The process is divided into fixed-size pages, and physical memory is divided into equal-size frames. A page can be placed in any free frame, so the process does not need to occupy one contiguous area of physical memory.

A logical address is divided into page number + offset. The page number is used to look up the corresponding frame number in the page table, and then the same offset is used inside that frame.

Logical address: (page number, offset) → Page table → Physical address: (frame number, offset)

Physical vs logical address

This slide is explaining how a program moves from source code to execution in physical memory, and more importantly, when addresses are decided.

On the left, you have a C program. Suppose the program contains something like variables, instructions, function calls, etc. In Stage 1, the program is compiled. The compiler/assembler produces an executable file, shown here as a.out. Inside that executable, instructions may contain addresses such as:

Load 1000
Add  ...
Store 1080

These addresses are the addresses the program was generated with. At this stage, the program is just a file on disk; it is not yet running in RAM.

Then comes Stage 2: Run. When you type something like:

./a.out

the operating system loads that executable into physical memory and starts executing it.

The important issue shown on the right is this: the compiler may have generated an instruction referring to address 1000, but when the program actually runs, the OS may place the process somewhere completely different in physical memory because some memory locations are already occupied.

For example, imagine the executable assumes:

Load from address 1000

But when it is loaded, the available physical-memory region begins at address 5000.

Then we cannot blindly access physical address 1000, because that might belong to another process or to the OS. Somehow, address 1000 used by the program must be translated to the correct physical location.

For example:

Logical address 1000 → Physical address 6000

if the process has been loaded with a base of 5000.

This is exactly where address binding / relocation / memory management comes in.

The circled part in the middle saying something like "10 mins → 1 year → 5 years" is making another important point: there can be a huge time gap between compilation and execution. You might compile a program today and execute the same executable months or years later. The compiler therefore cannot reliably know where in physical RAM the program will be placed when it eventually runs.

That is why modern systems generally work with logical/virtual addresses rather than forcing the compiler to know actual RAM addresses.

So the flow is basically:

C source → Compiler/Assembler → Executable (a.out) → Loader → Physical Memory → Execution

The main idea of this slide is therefore:

The addresses present in the executable do not necessarily have to be the final physical-memory addresses. The program can be compiled at one time and loaded anywhere in physical memory much later, so we need some mechanism to relocate/translate addresses when the program executes.

This idea will directly lead into compile-time binding, load-time binding, execution-time binding, and eventually base/bound registers and paging.

04

Everything on paging

When a program is compiled and executed, the process is given its own virtual or logical address space. The CPU generates addresses within this virtual address space rather than directly using physical RAM addresses. In a 32-bit system, the virtual address space can range from 0 to (232 − 1), giving about 4 GB of virtual address space. However, this does not mean the process actually occupies 4 GB of physical memory.

Only some parts of the virtual address space are actually used. The lower region generally contains the program’s code and data, followed by the heap, which is used for dynamic memory allocation such as malloc(). The stack is placed near the higher-address end and grows in the opposite direction. A large portion of the virtual address space between the heap and stack may remain unused, which is why the diagram shows most of the space as empty.

Pages, Frames, and the Page Table

The process’s virtual memory is divided into equal-sized blocks called pages, and physical memory is divided into equal-sized blocks called frames. The page size and frame size are always the same; in the slide, each one is 1 KB.

The important part is that the pages of a process do not need to be stored next to each other in physical memory. A page containing code may go into one frame, a heap page into another frame far away, and stack pages into completely different frames. So even though the process sees one continuous virtual address space, its actual data can be scattered across RAM.

The OS keeps track of which virtual page is stored in which physical frame using a page table. So when the CPU generates a virtual address, the system finds the page number, looks up the corresponding frame number, and accesses that frame in physical memory.

This is why paging avoids the major problem of external fragmentation. The OS does not need one large continuous free region for the whole process; it only needs individual free frames of the required fixed size. Also, physical memory may contain things belonging to many different processes, as well as memory used by the OS itself, all mixed together in different frames.

The important idea is that the addresses generated by the CPU are logical addresses. These addresses must be translated into actual physical addresses in RAM before memory can be accessed. Therefore, each process can behave as if it has its own independent memory space, while the operating system and hardware handle the mapping of the used portions of that virtual address space to physical memory.

Understanding Heap and Stack Growth

Think of the virtual address space like a number line.

At the bottom are small addresses like 1000, 2000, 3000. At the top are large addresses like 9000, 10000.

The heap usually starts near the lower addresses and grows toward larger addresses when you use things like malloc().

Theory: Dividing a Binary Address by a Power of Two

For any non-negative integer N written in binary, division by 2p splits its bits into two parts:

  • Last p bits = remainder.
  • Remaining higher-order bits = integer quotient.

N = quotient × 2p + remainder   (0 ≤ remainder < 2p)

In byte-addressable paging, if the page size is 2p bytes, the last p bits of a logical address give the page offset. The remaining bits give the page number. For an m-bit logical address, the page-number field therefore has m − p bits.

The virtual page number selects a row; the PFN and control/status fields together form that page's PTE. The virtual page index labels the row rather than being an additional field stored in each entry.

These are extra control/status bits stored in each Page Table Entry (PTE) along with the PFN/frame number.

Valid bit tells whether that page belongs to the process’s legal virtual address space. If valid = 0, the address is invalid for that process.

Protection bit(s) tell what operations are allowed on that page, such as read, write, or execute. For example, a code page may be readable and executable but not writable.

Present bit tells whether the page is currently loaded in physical memory. If present = 1, the PFN/frame number can be used. If present = 0, the page is not currently in RAM, and accessing it causes a page fault.

Referenced bit tells whether the page has been accessed recently. Hardware usually sets it when the page is read or written. The OS uses this information in page-replacement algorithms to decide which pages are good candidates to remove.

Dirty bit tells whether the page has been modified after being loaded into RAM. If dirty = 1, the page has changed, so before removing it from RAM, the OS may need to write it back to disk. If dirty = 0, it can often be discarded without writing it back.

So a PTE is conceptually like:

PFN + Valid + Protection + Present + Referenced + Dirty

The PFN says where the page is, while the other bits say whether it is legal, currently present, allowed to be accessed in certain ways, recently used, or modified.

This is a conceptual layout; actual PTE fields and terminology vary by architecture. Here, valid means the address is legal, while present means the page is resident in RAM.

Multilevel paging

This shows the main problem with single-level paging and why multi-level paging is needed.

The program shown is tiny. Its actual memory requirement may be only a few dozen bytes: some code, a little static data, some stack space, and 4 bytes from malloc(4). But suppose the process has a very large virtual address space, say 32-bit. Then the page table must conceptually have an entry for every possible virtual page, even though the process is using only a tiny fraction of them.

That creates a ridiculous situation: the actual process may be only around 35–50 bytes, but its page table can occupy megabytes. Most of those page-table entries correspond to the huge unused region between heap and stack, so they are simply invalid/unmapped entries. In other words, the page table is full of entries that basically say, “this virtual page is not being used.”

The 35–50 bytes describe an illustrative amount of useful program content, not a real process's total memory footprint. Actual allocations use whole pages, and executable files, libraries, stack setup, and allocator metadata add overhead.

The diagram with code and heap near one end and stack near the other shows exactly this. Only a few virtual pages near the code/heap and stack are actually required. The enormous middle region is unused. But in a single-level page table, entries for all those unused virtual pages still exist. So we waste memory storing a huge number of invalid PTEs.

The solution is multi-level paging. Instead of storing one gigantic page table containing millions of entries, we divide the page table itself into smaller chunks. Then we create an upper-level table that tells us which of those smaller page-table chunks actually exist.

The important benefit is that we do not allocate the lower-level page-table chunks corresponding to huge unused portions of the virtual address space. If the middle 99% of the virtual address space is unused, we simply do not create page-table chunks for that region. We create lower-level page tables only for the regions containing useful pages such as code, heap, and stack.

So the whole motivation is:

Single-level paging

Huge page table, lots of useless invalid entries.

Multi-level paging

Break the page table into parts and create only the parts that are actually needed.

That is why multi-level paging can save a massive amount of memory when the virtual address space is large but the process actually uses only a small portion of it.

Worked Explanation: Three-Level Paging

This example shows how a single large page table can be divided into smaller chunks and organized using additional levels of page tables. The key is to understand why the 32-bit logical address becomes 6 + 8 + 8 + 10 bits, and how those fields guide translation to a physical address.

1. Start with Single-Level Paging

The logical address is 32 bits, and memory is byte-addressable, so the logical address space contains 232 bytes. The page size is 210 bytes = 1 KB, which requires a 10-bit offset. The remaining 22 bits identify the virtual page.

Number of virtual pages = 232 / 210 = 222

A single-level page table therefore has 222 entries. This can consume considerable memory even when most virtual pages are unused. At this stage, the address split is 22 page-number bits + 10 offset bits.

2. Divide the Page Table to Obtain Two Levels

Divide the original table into chunks of 28 = 256 entries. Selecting an entry inside a chunk takes 8 bits. Since the original table contains 222 entries, there are 222 / 28 = 214 chunks. An upper-level table has one entry pointing to each possible chunk.

The logical address is now split into 14 bits for the upper-level index, 8 bits for the lower-level index, and 10 bits for the offset. The first 14 bits select a pointer to a lower-level table; the next 8 bits select a PTE within it. However, the upper-level table still contains 214 entries, so it is itself a candidate for subdivision.

3. Divide Again to Obtain Three Levels

Divide that 214-entry upper-level table into chunks of 256 entries each. This creates 214 / 28 = 26 = 64 possible chunks. Introduce a new root table with 64 entries, one pointer per chunk. Numbering the levels from this new root, Level 1 uses 6 bits, Level 2 uses 8 bits, and Level 3 uses 8 bits.

32-bit logical address = L1 (6 bits) + L2 (8 bits) + L3 (8 bits) + Offset (10 bits)

4. Walk the Tables to Obtain a Physical Address

The page-table base register gives the physical address of the first-level table. The first 6 bits select one of its 64 entries, which provides the base address of a second-level table. The next 8 bits select one of that table's 256 entries, giving the base of a third-level table. The next 8 bits select the final PTE, which supplies the physical frame number. At each level, selecting an entry means using the table base plus the index multiplied by that level's entry size.

The final 10 bits are the byte offset. They pass through unchanged, identifying the same byte position within the selected frame. This example assumes a 30-bit physical address, so the physical frame number occupies 30 − 10 = 20 bits. Concatenating that frame number with the 10-bit offset gives the physical address. Invalid entries or disallowed accesses cause a fault rather than a successful translation.

Physical address = (20-bit frame number | 10-bit offset) = PFN × 1024 + offset

5. Why the Extra Levels Save Memory

A single-level table requires 222 entries even if the process uses only a tiny fraction of its virtual address space. With this three-level scheme, the root contains only 64 entries, and lower-level tables are allocated only for regions that need mappings. An invalid pointer in an upper-level entry can represent a whole unused region, eliminating the need to allocate the tables below it. The maximum counts are 64 second-level tables and 214 third-level tables; sparse processes need only a subset.

GATE takeaway: Neither the 32-bit logical address nor the 1 KB page size changes. Only the 22-bit page number is split into 6 + 8 + 8 bits to allow hierarchical lookup and omit unnecessary lower-level tables. The chosen chunk size is 256 entries, not 256 bytes; each lower-level table fits in a 1 KB page if its entries are 4 bytes each. The example's field split does not itself specify entry sizes.

Page Fault

Suppose the CPU generates an address, but the page containing that address is not currently in Main Memory (RAM). Accessing that nonresident page causes a page fault, transferring control to the operating system.

For a legal access to a page stored on disk, the OS brings the required page from Secondary Storage into Main Memory. It places the page in an available frame, updates the page table with the frame number and marks the page as present. The interrupted instruction is then restarted, allowing the access to proceed.

In this example, page 0 contains logical addresses 0–99 and page 1 contains 100–199. Therefore, logical address 130 belongs to page 1, with offset 130 − 100 = 30. If page 1 is absent, the OS loads the entire page, rather than just the byte at address 130.

The example assumes a legal, disk-backed page. An illegal access is rejected rather than satisfied by loading a page. If no free frame is available, the OS must first choose a page to replace; a modified victim may need to be written back before its frame is reused.

Page Replacement Algorithms

A page replacement algorithm selects a resident page to remove when a page fault must be serviced and no free frame is available to the requesting process. The removed page is called the victim page; its frame is reused for the required page.

The aim is to reduce page faults while keeping replacement overhead low. A reference string records the page numbers accessed by a process, in order.

  1. Page present: it is a hit. Update any reference information required by the policy.
  2. Page absent, free frame available: count a fault and load the page into the free frame. No victim is needed.
  3. Page absent, no free frame available: count a fault, choose a victim, write it back if necessary, and load the requested page into its frame.
  4. Update the affected page-table entries and invalidate stale TLB entries as needed, then restart the interrupted instruction.

Fault versus replacement: Every replacement here occurs because of a fault, but an initial load into a free frame is also a fault. A clean victim can be discarded if its contents can be recovered; a dirty victim may require a write-back.

1. FIFO — First In, First Out

Replace the page that was loaded into memory earliest. Maintain a queue from oldest to newest: append a newly loaded page at the rear and remove the front page when replacement is required.

A hit does not change the queue order. FIFO tracks arrival time, so even a frequently used page may be removed if it is the oldest.

Victim = page with the earliest load time

FIFO is simple to implement, but it can exhibit Belady's anomaly: adding frames can increase the number of page faults.

Understanding the FIFO Queue

In the slide, the resident pages are arranged in loading order, from the oldest on the left to the most recently loaded on the right. These are page numbers, not ages or priorities.

If a missing page 8 must be loaded and these are all the available frames, evict page 5 and append page 8. The queue becomes:

3, 4, 7, 9, 11, 2, 1, 15, 8

Even if page 5 was accessed just before this fault, FIFO still evicts it because its load time is the earliest. A hit on page 5 would not make it the newest page.

2. Optimal — OPT / MIN

Replace the resident page whose next reference lies farthest in the future. A page that is never referenced again is the best victim. If several pages are never used again, any one of them may be chosen.

Victim = page used farthest in the future

OPT gives the minimum possible fault count for a fixed reference string, frame count, and initial resident state. It requires knowledge of future references, so it is used as a theoretical benchmark rather than a general online policy.

Look forward from the current position. OPT does not choose the page with the fewest total future accesses; it compares the time of each page's next access.

Victim = page not accessed for the longest time

Belady's Anomaly and the Stack Property

Belady's anomaly occurs when increasing the number of frames causes more page faults for the same reference string and replacement policy.

A stack algorithm has the inclusion property: after each reference, the resident set with m frames is a subset of the resident set with m + 1 frames, starting empty under consistent policy choices. Therefore, adding a frame cannot turn a hit in the smaller memory into a fault in the larger memory.

LRU and OPT are stack algorithms and do not suffer from Belady's anomaly (use consistent tie-breaking for OPT). FIFO is not a stack algorithm and may suffer from the anomaly. More frames do not necessarily improve FIFO on every reference string.

A system uses 3 page frames for storing process pages in main memory. It uses the Least Recently Used (LRU) page replacement policy. Assume that all the page frames are initially empty. What is the total number of page faults that will occur while processing the page reference string given below?

4, 7, 6, 1, 7, 6, 1, 2, 7, 2

Solution: On a miss, count a page fault even if an empty frame is available. Once all three frames are occupied, replace the page whose last access is farthest in the past. Update recency on every access, including hits.

Q2. GATE CSE 2014 Set 1 · Question 33

Assume that there are 3 page frames which are initially empty. If the page reference string is 1, 2, 3, 4, 2, 1, 5, 3, 2, 4, 6, the number of page faults using the optimal replacement policy is ________.

1, 2, 3, 4, 2, 1, 5, 3, 2, 4, 6

Solution: Load a missing page into a free frame if one is available. Otherwise, replace the resident page whose next use is farthest in the future. A page that is never referenced again is the best victim.

  2. Step 4, page 4: page 2 is next used at step 5, page 1 at step 6, and page 3 at step 8. Replace page 3, whose next use is farthest away. The fault count becomes 4.

  5. Steps 9–10: pages 2 and 4 are present, so both accesses are hits.

Answer: 7. There are 4 hits and 4 replacements. Optimal can still reload an evicted page: page 3 faults again at step 8 because it was the best victim at step 4. Compare next-use positions rather than assuming each distinct page faults only once.
